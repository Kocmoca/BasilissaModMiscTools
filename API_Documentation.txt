## 一、LuaEvents（跨 mod 事件通知）

其他 mod 通过 LuaEvents.{EventName}.Add(handler) 订阅，
本 mod 在适当时候通过 LuaEvents.{EventName}.Call(...) 触发。

------------------------------------------------------------------------------
### 1.1 建造系统
------------------------------------------------------------------------------

ModMiscToolBuildCompleted(playerID, unitID, plotIndex, itemType, itemCatagory, costModel)
  触发时机：BuildItemOnMap 成功执行完毕后
  参数：
    playerID     (number)  建造者玩家ID
    unitID       (number)  执行建造的单位ID（可能为nil）
    plotIndex    (number)  建造目标地块索引（可能为nil）
    itemType     (string)  建造的物件类型（如 "IMPROVEMENT_FARM"）
    itemCatagory (string)  物件分类："District"|"Building"|"Improvement"|"Route"|"Feature"|"Resource"|"Terrain"
    costModel    (string)  花费模型名称（对应 Kocmoca_Build_CostModels.CostModel，可能为nil）
  示例：
    LuaEvents.ModMiscToolBuildCompleted.Add(function(playerID, unitID, plotIndex, itemType, itemCatagory, costModel)
        print("Build completed: " .. itemType .. " at plot " .. (plotIndex or "nil"))
    end)

### 1.2 面板状态
------------------------------------------------------------------------------

ModMiscToolExtensivePanelOpened(playerID, unitID)
  触发时机：ExtensiveUnitPanel（单位操作面板）打开时
  参数：
    playerID (number) 选中单位所属玩家ID，-1表示无选中
    unitID   (number) 选中单位ID，-1表示无选中

ModMiscToolExtensivePanelClosed()
  触发时机：ExtensiveUnitPanel 关闭时
  参数：无

ModMiscToolInfoPanelOpened()
  触发时机：帝国信息面板（InfoPanel）打开时
  参数：无

ModMiscToolInfoPanelClosed()
  触发时机：帝国信息面板关闭时
  参数：无

ModMiscToolSidebarExpanded()
  触发时机：左侧工具栏展开时
  参数：无

ModMiscToolSidebarCollapsed()
  触发时机：左侧工具栏折叠时（折叠时会自动关闭已打开的InfoPanel）
  参数：无

### 1.3 城市与领土
------------------------------------------------------------------------------

ModMiscToolCityOwnerChanged(oldPlayerID, newPlayerID, cityID, iX, iY, plotIndex)
  触发时机：城市从一个玩家转移到另一个玩家（通过移除+添加检测）
  参数：
    oldPlayerID (number) 原所有者玩家ID
    newPlayerID (number) 新所有者玩家ID
    cityID      (number) 城市ID
    iX, iY      (number) 城市坐标
    plotIndex   (number) 城市地块索引

ModMiscToolReturnCityToDefeated(oldOwnerID, newOwnerID, cityID, iX, iY)
  触发时机：已被击败的玩家通过城市转移复活
  参数：
    oldOwnerID (number) 转让方玩家ID
    newOwnerID (number) 接收方（复活方）玩家ID
    cityID     (number) 城市ID
    iX, iY     (number) 城市坐标

ModMiscToolLastCityCaptured(playerID, cityID)
  触发时机：玩家失去最后一座城市（判定为被击败）
  参数：
    playerID (number) 被击败的玩家ID
    cityID   (number)  最后失去的城市ID

### 1.4 单位与战斗
------------------------------------------------------------------------------

ModMiscToolCombat(pCombatResult, iX, iY, plotIndex)
  触发时机：任意战斗结算完成后（由 Mod Misc Tool 监听官方 Events.Combat 后重新分发）
  参数：
    pCombatResult (table)  原始 CombatResultParameters 战斗结果表
    iX, iY       (number)  战斗发生地块坐标，可能为 nil
    plotIndex    (number)  战斗发生地块索引，可能为 nil
  说明：
    其他 mod 可改用 LuaEvents.ModMiscToolCombat.Add(handler)，
    避免直接注册官方 Events.Combat 造成重复解析和全局函数名冲突。
    handler 仍可通过 pCombatResult 读取：
      ATTACKER / DEFENDER -> ID -> player, id, type
      LOCATION -> x, y
      DAMAGE_TO 等官方字段
    当前其他 mod 的典型用法见本节末尾“战斗接口迁移说明”。

ModMiscToolUnitKilledInCombat(killedPlayerID, killedUnitID,
                               killerPlayerID, killerUnitID,
                               iX, iY, plotIndex, pCombatResult)
  触发时机：单位 vs 单位战斗中，Mod Misc Tool 通过官方 Events.Combat 判定有单位阵亡后分发
  参数：
    killedPlayerID (number) 阵亡单位所属玩家ID
    killedUnitID   (number) 阵亡单位ID
    killerPlayerID (number) 击杀者所属玩家ID
    killerUnitID   (number) 击杀单位ID
    iX, iY         (number) 战斗发生地块坐标，可能为 nil
    plotIndex      (number) 战斗发生地块索引，可能为 nil
    pCombatResult  (table)  原始 CombatResultParameters 战斗结果表
  说明：
    该事件只对应“单位攻击单位”的战斗，用于替代官方 Events.UnitKilledInCombat。
    killer/killed 的对应关系由 Mod Misc Tool 根据 CombatResult 的
    ATTACKER / DEFENDER 自动判定。一个单位在同一场战斗中被判定阵亡时只触发一次。
    单位攻击区域等非单位对单位的战斗，请使用 ModMiscToolDistrictAttacked。

ModMiscToolDistrictAttacked(attackerPlayerID, attackerComponentID,
                            districtOwnerPlayerID, districtID,
                            districtType, cityID,
                            iX, iY, plotIndex, pCombatResult)
  触发时机：任何攻击方对区域类型目标（ComponentType.DISTRICT）发动攻击后分发
  参数：
    attackerPlayerID      (number) 攻击方玩家ID
    attackerComponentID   (number) 攻击方 component ID；攻击方是单位时即 unitID
    districtOwnerPlayerID (number) 区域所属玩家ID
    districtID            (number) 区域 component ID
    districtType          (string) 区域类型，如 "DISTRICT_CITY_CENTER"、"DISTRICT_ENCAMPMENT"
    cityID                (number) 该区域所属城市ID；无法取得时为 nil
    iX, iY                (number) 战斗发生地块坐标，可能为 nil
    plotIndex             (number) 战斗发生地块索引，可能为 nil
    pCombatResult         (table)  原始 CombatResultParameters 战斗结果表
  说明：
    该事件用于区分“攻击区域”和“单位击杀单位”。
    区域类型通过 DISTRICT 类型的 Component ID 或战斗地点反查；
    城市ID通过区域对象 GetCity():GetID() 获取。

ModMiscToolUnitLostInCombat(playerID, unitID, pCombatResult)
  触发时机：单位在战斗中阵亡（兼容旧接口，仍然触发）
  参数：
    playerID      (number) 单位所属玩家ID
    unitID        (number) 阵亡单位ID
    pCombatResult (table)  战斗结果数据（CombatResultParameters格式）
  说明：
    该事件只包含阵亡单位，不包含击杀者信息，且不区分是单位对单位还是攻击区域。
    新代码建议：
      单位对单位 -> ModMiscToolUnitKilledInCombat
      攻击区域   -> ModMiscToolDistrictAttacked

ModMiscToolUnitUpgraded(playerID, oldUnitID, newUnitID)
  触发时机：单位升级完成
  参数：
    playerID  (number) 玩家ID
    oldUnitID (number) 升级前单位ID
    newUnitID (number) 升级后单位ID

战斗接口迁移说明：
  当前其他 mod 中常见的战斗处理方式为直接注册 Events.Combat：
    Events.Combat.Add(OnCombat)
  然后在 OnCombat(pCombatResult) 中读取：
    pCombatResult[CombatResultParameters.LOCATION]
    pCombatResult[CombatResultParameters.ATTACKER][CombatResultParameters.ID]
    pCombatResult[CombatResultParameters.DEFENDER][CombatResultParameters.ID]
    pCombatResult[CombatResultParameters.DAMAGE_TO] 等
  这些 mod 可以逐步改为：
    LuaEvents.ModMiscToolCombat.Add(OnCombat)
  从而由 Mod Misc Tool 统一监听官方战斗事件，避免每个 mod 各自注册 Events.Combat。
  如果只需要“谁击杀了谁”，应优先改为订阅：
    LuaEvents.ModMiscToolUnitKilledInCombat.Add(OnUnitKilledInCombat)
  如果处理“攻击区域”，应订阅：
    LuaEvents.ModMiscToolDistrictAttacked.Add(OnDistrictAttacked)

## 二、ExposedMembers.ModMiscToolScript（Gameplay 层 API）
==============================================================================

这些接口在 Gameplay 脚本环境中可用，供其他 mod 的 Gameplay 脚本调用。
通过 ExposedMembers.ModMiscToolScript.{name} 访问。

------------------------------------------------------------------------------
### 2.1 数据表（直接读取）
------------------------------------------------------------------------------

ModMiscToolScript.allUnitData
  类型：table  结构：allUnitData[playerID][unitID] = { unitType, promotionClass,
        iX, iY, plotIndex, expPoint, promotions, militaryFormation, damage,
        removed, upgradeTo, upgradeFrom, combatDeathX, combatDeathY }
  说明：所有单位的运行时数据缓存，由 ModTool.lua 维护

ModMiscToolScript.defeatedPlayers
  类型：table (array)  元素：playerID (number)
  说明：已被击败的玩家ID列表

ModMiscToolScript.playerCitiesInfo
  类型：table  结构：playerCitiesInfo[playerID][cityID] = { iX, iY, plotIndex }
  说明：所有城市的坐标信息缓存

ModMiscToolScript.buildingsOfDistrict
  类型：table  结构：buildingsOfDistrict[districtType] = { buildingType, ... }
  说明：每个区域类型可建造的建筑列表（从数据库 Buildings.PrereqDistrict 生成）

------------------------------------------------------------------------------
### 2.2 查询与通用辅助函数
------------------------------------------------------------------------------

GetUnitData(playerID, unitID)
  返回：unitData (table) 或 nil
  说明：获取指定单位的缓存数据

GetPlayerAssetNumber(playerID, assetType)
  返回：number（该类型资产的数量）
  参数：assetType 为建筑/区域/改良设施类型字符串
  说明：获取某玩家拥有的特定类型资产总数；返回值来自 assetType -> plotIndex 字典计数。
        返回 0 时会输出 [ModMiscTool][Asset] 日志。

GetPlayerAssetPlotIndexes(playerID, assetType)
  返回：table（plotIndex 数组，已排序）
  说明：获取某玩家某类资产所在的所有 plotIndex

GetPlotAssetTypes(playerID, plotIndex)
  返回：table（assetType 数组，已排序）
  说明：获取某玩家在某 plot 上持有的所有 assetType

HasPlayerAsset(playerID, assetType, plotIndex)
  返回：boolean
  说明：O(1) 判断某玩家是否在某 plot 持有某类资产

TableContains(testTable, testElement)
  返回：boolean
  说明：判断数组表中是否包含指定元素

PlotIndexToXY(plotIndex)
  返回：iX, iY 或 nil, nil
  说明：通过地块索引获取坐标

GetCityPlotIndex(city)
  返回：plotIndex 或 nil
  说明：通过城市对象获取城市中心地块索引

GetUnitCoordinate(unit)
  返回：iX, iY 或 nil, nil
  说明：通过单位对象获取坐标；单位不存在或已阵亡时返回 nil

DamageToUnit(targetUnit, damageFromPlayer, damageNum, isDamageToOwner)
  返回：boolean（目标单位是否阵亡）
  说明：对单位造成伤害；damageNum 为负数时可治疗。
        默认只伤害敌方单位，isDamageToOwner=true 时才允许伤害同玩家单位。

AoeAllUnitsForPlot(aoeX, aoeY, aoeOwner, aoeAmount, aoeRadius)
  说明：对范围内所有敌方单位造成范围伤害

### 2.3 判定函数
------------------------------------------------------------------------------

IsPlayerMatchRequirement(CaseType, playerID)
  返回：boolean
  说明：检查玩家是否满足 CaseType 的全部硬性要求
        （TraitType, TechType, CivicType, GoldAmount, FaithAmount,
         ResourceType/Amount, PlayerPropertyType/Num）

IsUnitMatchRequirement(unitID, CaseType, playerID)
  返回：boolean
  说明：检查单位是否满足 CaseType 的要求
        （UnitType, AbilityType, UnitPropertyType/Num）

IsPlotMatchRequirement(plotIndex, CaseType, playerID)
  返回：boolean
  说明：检查地块是否满足 CaseType 的全部要求
        （TerrainType, FeatureType, ResourceType, PlotOwnerList, ItemCatagory）

------------------------------------------------------------------------------
### 2.4 操作函数
------------------------------------------------------------------------------

BuildItemOnMap(playerID, unitID, plotIndex, itemType, itemCatagory, costModel)
  说明：在地图上执行建造操作
  流程：
    1. 扣除花费（ProcessBuildCost）：建造次数/金币/信仰/资源
    2. 放置物件（ProcessBuildEffect）：根据 itemCatagory 执行对应建造逻辑
    3. 扣除单位移动力（根据 CostModel.UnitMovement 或全部剩余）
    4. 触发 ModMiscToolBuildCompleted 事件
  注意：所有需求检查应在调用此函数前完成（本函数不做验证）

ChangeBuildCharge(playerID, unitID, amount)
  说明：修改单位的建造次数属性
  参数：amount > 0 增加，amount < 0 减少

SaveAsset(playerID, assetType, plotIndex)
  说明：向 asset 缓存写入“某玩家在某 plot 持有某 asset”
  参数：assetType 为建筑/区域/改良设施类型字符串；plotIndex 为地块索引
  说明：同时更新 playerAssetsInfo 与 playerPlotsInfo 两个字典索引，不产生重复计数

RemoveSpecificAssets(playerID, assetType, plotIndex)
  说明：移除“某玩家某类 asset 在某 plot”的记录
  参数：assetType、plotIndex 同上

RemoveAssetFromPlot(playerID, assetType, plotIndex)
  说明：从某 plot 移除某玩家的某类 asset 记录
  说明：与 RemoveSpecificAssets 使用同一底层删除逻辑

### 2.5 强制生效表（调试/override）

ModMiscToolScript.forceValidPlots

ModMiscToolScript.forceValidUnits

ModMiscToolScript.forceValidPlayers

### 2.6 WorldBuilder（地图编辑器）接口（Gameplay 层）
------------------------------------------------------------------------------

访问方式：
  ExposedMembers.ModMiscToolScript.WorldBuilderAPI

说明：接口模块是独立文件 ModTool_WorldBuilderAPI.lua，由 gameplay 脚本
      ModTool.lua include（运行在 Gameplay Lua 状态），再由 Initialize()
      暴露到 ExposedMembers.ModMiscToolScript.WorldBuilderAPI 供 UI 层与
      其他 mod 使用；与 mod 内 ExtensiveUnitBuild.lua 直接调用
      WorldBuilder.* 的路径保持一致。
      不做 API 存在性检测——方法名与参数顺序都取自原版地图编辑器的实际
      调用，属于已知接口，直接调用（例如 SetPlayerLeader(playerID,
      leaderType, civType, civLevel)）。

IsActive()
  返回：boolean
  说明：是否处于地图编辑器模式，仅作状态参考，不作为接口可用性判定。
        这些接口在普通对局（非地图编辑器）中同样可以直接调用，
        测试面板就是在普通对局环境下验证它们的。

PlayerManager（文明 / 领袖 / 时代 / 金币 / 信仰 / 科技 / 市政 / 起始位置）
  AddPlayer(isAI)                           -> playerID（失败返回 -1）
  RemovePlayer(playerID)                    -> UninitializePlayer
  IsPlayerInitialized(playerID)             -> boolean
  GetPlayerConfig(playerID)                 -> { Name, Civ, Leader, CivLevel, Era, Gold, Faith, IsHuman, IsBarbarian, IsFullCiv, ... }
  GetSlotStatus(slotIndex)                  -> SlotStatus.*
  SetPlayerLeader(playerID, leaderType, civType, civLevel)
  SetPlayerEra(playerID, eraType)
  SetPlayerGold(playerID, amount) / SetPlayerFaith(playerID, amount)
  PlayerHasTech / SetPlayerHasTech / PlayerHasCivic / SetPlayerHasCivic
  SetPlayerStartingPosition / ClearPlayerStartingPosition / ClearStartingPosition
  GetStartPositionInfo / GetStartPositionPlayer
  SetRandomMajorStartingPosition / SetRandomMinorStartingPosition
  SetLeaderStartingPosition / SetCivilizationStartingPosition

CityManager（城市 / 区域 / 建筑 / 地块归属）
  CreateCity(playerID, plot) / RemoveCityAt(plot) / RemoveCity(city) / GetCity(playerID, cityID)
  GetPlotOwner(plot) / SetPlotOwner(plot, ownerID)
  GetCityValue / SetCityValue / CreateDistrict / RemoveDistrict
  GetDistrictValue / SetDistrictValue / CreateBuilding / RemoveBuilding

MapManager（地形 / 特征 / 资源 / 改良 / 路线 / 河流 / 悬崖 / 可见度）
  SetTerrainType / SetFeatureType / CanPlaceFeature / GetFeaturePlacementPlotList
  IsWonderTooClose / SetResourceType / CanPlaceResource
  SetImprovementType / CanPlaceImprovement / IsImprovementPlaceable / SetImprovementPillaged
  SetRouteType / SetContinentType / EditRiver / EditCliff / DoesPlotBorderRiver
  GetContinentPlots / SetCoastalLowland / SetPlotValue
  SetAllRevealed(revealed, playerID) / SetRevealed(plot, revealed)

UnitManager
  CreateUnit(unitTypeIndex, playerID, plot) / RemoveUnitAt(plot) / RemoveUnit(unit)

ConfigurationManager / ModManager（地图级配置与文本）
  SetMapValue / GetMapValues / GetKeyStringPairByIndex / SetKeyStringPairByIndex
  SetString / RemoveString

WorldBuilder 顶层（撤销 / 重做 / ID / 模式）
  StartUndoBlock / EndUndoBlock / Undo / Redo / CanUndo / CanRedo
  GetID / SetID / GenerateID / IsMod / SetMod
  SetWBAdvancedMode / GetAdvancedMode
  SetVisibilityPreviewPlayer / ClearVisibilityPreviewPlayer

示例（把某个玩家改成数据库里的罗马 + 默认领袖）：
  local api = ExposedMembers.ModMiscToolScript.WorldBuilderAPI
  if api.IsActive() then
      api.SetPlayerLeader(playerID, "LEADER_TRAJAN", "CIVILIZATION_ROME",
          "CIVILIZATION_LEVEL_FULL_CIV")
  end

### 2.6.1 地图重建（MapRebuild）
------------------------------------------------------------------------------

访问方式：
  ExposedMembers.ModMiscToolScript.MapRebuild.RebuildMap(options)
  ExposedMembers.ModMiscToolScript.RebuildMap(options)   -- 直接函数别名

说明：独立文件 ModTool_MapRebuild.lua，由 ModTool.lua include 并暴露。
      负责“整图重做”：海陆布局（Archipelago / Small Continents / Pangaea /
      Continents）、浅海/深海、河流、湖泊、以及本项目自创的“浅海大河”。
      Exoplanet Homeland 只调用本接口，不再维护地图生成代码。

RebuildMap(options) -> true, details / false, error
  options.Layout          string  地图脚本名（"Archipelago"）或布局键
  options.SpawnKey        string  出生点表属性键（可选；默认 ModMiscMapRebuild_spawns）
  options.CandidateKey    string  出生点候选表属性键（可选）
  options.UnitSpawnKey    string  非幽灵玩家单位出生地表属性键（可选；
                                  默认 ModMiscMapRebuild_unit_spawns）
  options.Lakes           boolean 默认 true
  options.Rivers          boolean 默认 true
  options.BigRivers       boolean 默认 true
  options.LakeCount / RiverCount / BigRiverCount  number 可选，覆盖按地图尺寸算出的默认值
  options.WorldBuilder     table   可选，测试用 WorldBuilderAPI 替代

  details = {
    Layout, Land, Total, Lakes, Rivers, BigRivers,
    ClearedRivers, SpawnRepaired, SpawnCandidates, SpawnedPlayers, MovedUnits,
    BigRiverCells, LongestBigRiver
  }

  · 陆地/海洋按目标水陆比例用陆块中心 + 随机生长重建；
  · 靠陆地的水格改海岸，其余深海；
  · 河流/湖泊 = 完整移植原版 RiversLakes.lua（Expansion2）：
    GetRiverValueAtPlot / DoRiver / AddRivers / AddLakes / AddMoreLake / 转向表；
    河沿优先用 3 参数 TerrainBuilder.Set*OfRiver(plot, true, flowDirection)
    （不传自编 riverID），失败才退回 WorldBuilder EditRiver；水格一律跳过；
  · 大河 = 选离水最远的源头，铺一条从内陆到海边的 TERRAIN_COAST 单元格带
    · **稳定性结论（2026-10-21）**：大河不要复用原版河流的 GetRiverValueAtPlot/DoRiver
      寻路（会与原版河流相互干扰）；实机原生闪退 ReadTextureFromDisk 出现在改用原版取向之后，
      改成“山脉源头 + 随机 6 向 + 蜿蜒绕山”的独立算法后不再出现。

    （本项目自创，模拟宽阔大河/水上门户；深入内陆交给它）；原版河流只做短支流
    （源头离水范围 2/1），再运行原版 AddRivers ⇒ 原版河流成为大河的支流；
  · 校验/修复 SpawnKey 里的出生点，并把最多 32 个可用出生点写入 CandidateKey；
  · 非幽灵、地图上有单位的玩家（含城邦）：预设 UnitSpawnKey 出生格，UnitManager.PlaceUnit

------------------------------------------------------------------------------
### 2.7 幽灵玩家（Ghost Players）
------------------------------------------------------------------------------

背景：运行中的对局里用 PlayerManager():AddPlayer() 新增玩家会让引擎的 AI 外交子系统
      （GameCore::AI::Diplomatic::GetDiplomaticStateIndex）空指针闪退，因此本 mod 改为
      “开局多建、多余的搬到地图外”的方案：
        * 创建游戏界面（UI/Replacements/Civ6Common.lua 的前端 hook）把城邦数量拉满，并用
          Civ6Common 的 WriteCustomData 记下玩家原本选择的数量；
        * 进游戏后 ModTool_GhostPlayers.lua 按该数量保留城邦，把多出来的城邦玩家搬到地图外
          （UnitManager.InitUnit 放一个地图外开拓者，再清掉地图上的单位），得到一批
          “引擎认可、但不在图上”的玩家，即幽灵玩家。
        * 幽灵可用 GhostPlayers_CityStates.sql 复制城邦文明来扩容（引擎按城邦文明条数上限
          创建城邦玩家）。
      幽灵玩家池记录在存档属性里，随存档走；读老档不会重建池子。

—— 幽灵玩家的“新鲜度”：复活后必须立刻不再是幽灵（2026-10-15）——

背景（授权者实机）：幽灵被复活（拿到城市、回到地图上，例如定制附庸落地）之后，框架仍把它
当幽灵 ⇒ ①外交界面/外交条看不到这个新附庸；②点它的城市 banner 去开领袖场景时，该玩家又被
当幽灵挡下 ⇒ 场景半开，引擎那边 `BulkHide(true, "Diplomacy")` 之后再也等不到
`BulkHide(false)` ⇒ HUD 五组（WorldViewControls/HUD/PartialScreens/Screens/TopLevelHUD）
全部隐藏，也就是“UI 全部消失”。

两层处理：
  ① **兜底判定**：`IsGhostPlayer / IsCityStateGhostPlayer` 现在会检查“该玩家有没有城市”，
     有城市就直接返回 false（池子还没清也立刻不再被当幽灵；每条玩家只打一次日志）。
  ② **及时清池**：`RemoveGhostPlayerFromPool(playerID, reason)` /
     `RefreshGhostPoolsFromCities(reason)`（都挂在 ExposedMembers.ModMiscToolScript）——
     建城（CreateCityForGhostPlayer）与转城（TransferCityToGhostPlayer）成功后会立刻把它
     摘出两个池子；每回合开始再全量刷一次；其它 mod 落地完幽灵也可以主动调。
     `PlayerOwnsCity(playerID)` 一并导出，供判断用。

外交界面侧再加一道：幽灵在**界面入口**就被挡下（`OnOpenDiplomacyActionView`），
连 `InitializeView` 都不进 —— 这正是避免“半开 ⇒ HUD 只隐藏不恢复”的关键；
拒绝时如果发现 HUD 已经被隐藏，会顺手 `RestoreInGameUI()` 兜底恢复。

若真的遇到 HUD 全没了（旧版本留下的状态）：面板「恢复 UI」按钮，或调
`ExposedMembers.ModMiscToolUI.RestoreInGameUI()`（只强制取消隐藏那五组，不动引擎计数与输入栈）。

—— 【2026-10-15 授权者】两个池子 = 两种**附庸行为**（Vassal System 里的语义）——

| 池子 | 附庸行为 | 表现 |
|---|---|---|
| 主流幽灵池 | **正常玩家行为** | 会扩张、正常建造 |
| 城邦幽灵池 | **保守玩家行为** | 不扩张、建造的区域也少 |

* 玩家可以在面板里**二选一**；**“行为”才是选池子的依据**。
* 面板里“选文明”时把文明按主流/城邦分开列，只是为了**找文明方便** ——
  它和“选行为”是两件事，别把两者混为一谈（代码里 `branch` 就是行为：
  `'major'` = 正常行为 = 主流池；`'citystate'` = 保守行为 = 城邦池）。
* 取幽灵**严格按行为选池**（`TransferCityToGhostPlayer` 的第 7 个参数 `behavior` 决定池子；
  没给 behavior 时才退回"按目标文明等级猜"的老行为。Vassal System 一律传行为）。
  ⚠️ 2026-10-17 更正：**等级（CivLevel）与选池是两件事**——等级看文明的类型
  （主流文明 ⇒ `FULL_CIV`、城邦文明 ⇒ `CITY_STATE`），行为只看该从哪个池取人。跨池兜底默认关（`GHOST_ALLOW_POOL_FALLBACK = false`）——
  选了保守就该给保守幽灵，宁可如实报错也不偷偷换行为。
* **城邦幽灵池默认不申报（0）**：它会把创建游戏界面的城邦数量抬高，很多玩家只看那个数字就投诉。
  但框架按“城邦幽灵池存在”来写：声明表里那一列（默认 `Vassal System/Vassal_GhostDemand.sql`
  的 `CityStateGhosts`）改成 8 即可开回来
  （其它 mod 也可以用 `ModMiscToolRegisterCityStateGhostDemand` 申报，见 §2.8b）。
  没开回来时，选保守行为会在确认前提示“所选行为当前没有可用的幽灵玩家”，池子空但流程不假成功。
  面板文案（2026-10-15 授权者定）：两个行为按钮就叫**正常行为 / 保守行为**，不写机制说明；
  定制附庸栏顶部与信息行**不放文字**；行为每次都要显式点一次（进入配置步骤不预选行为）。
* 城邦池相关 API（`GetCityStateGhostPlayers` / `ClaimAvailableCityStateGhostPlayer` …）全部保留。


—— 【2026-10-15 授权者】幽灵“原身份”台账 + 自动城邦化 + 读档语义更正 ——

**原身份台账**（`ModTool_GhostPlayers.lua`，存档属性 `kocmoca_modmisctool_ghost_identities`）：
  * 玩家创建时引擎会记下它的**原文明/原领袖**，之后改 `PlayerConfigurations` 也改不掉引擎那份 ——
    外交界面/议会按引擎记录显示，幽灵被改成别的文明时就会和场上真正的该文明玩家**显示冲突**；
  * 所以幽灵**进池子的那一刻**把 `playerID → { civ, leader, turn }` 记进台账（只记一次，
    之后无论怎么改身份都不覆盖）；
  * 查询：`GetGhostOriginalIdentities()` / `GetGhostOriginalIdentity(id)` /
    `GetGhostOriginalIdentityScore(id, civType, leaderType)`（原文明+原领袖全中 = 2、中一个 = 1、
    没台账 = nil）。Vassal System 取幽灵时按 `原身份 ×10 + 当前身份` 排序 ⇒ **优先原身份相符的**，
    外交界面不会冲突；这类幽灵通常也不用改身份 ⇒ 建城后免读档。

**自动城邦化**：时机 = **本地玩家建立第一座城市时**（`Events.CityAddedToMap` +
`TryAutoConvertGhostsOnFirstCity`，只做一次、写 `kocmoca_modmisctool_ghost_autoconvert_done` 落档）：
  * 城邦化后幽灵不再带“大文明外交 footprint”（外交界面 / 世界议会都不受影响，已实机验证）；
  * 开局就做完，之后玩家要附庸时池子里已经是“城邦幽灵”，配合原身份匹配多数请求可免读档；
  * 老档（本地玩家已有 >1 城）不补做，只标记完成；开关 `GHOST_AUTO_CONVERT_ON_FIRST_CITY`
    2026-10-26 恢复为 true —— 这是唯一放行的城邦化入口（见 §2.8c-2）。

—— 【2026-10-17 授权者】开拓者归位：城市落地时把**地图外的开拓者移动进城市** ——

现象：幽灵化时用 `InitUnit(UNIT_SETTLER, -1, -1)` 把玩家搬到地图外垫底，这个开拓者一直留在地图外。
AI 一次只盯一个开拓者 ⇒ 玩家（定制附庸）落地后**不再自己找地建城**。
（口径更正 2026-10-17：**能自己建城的是「普通行为」= 主流等级 `FULL_CIV`**；
保守行为 = 城邦级 `CITY_STATE`，引擎按城邦处理、不扩张，本来就不该自己建城 ——
开拓者归位只是把"卡住的开拓者槽位"还原，不代表保守行为会去建城。）

处置（授权者定案）：**城市添加到地图的事件触发时判断是否为幽灵，是则把该玩家地图外的开拓者
移动进这座城市**。实现在 `ModTool_GhostPlayers.lua`：

  * 机制（授权者口径）：**遍历该玩家的单位 ⇒ 找"开拓者类型"且"坐标 < 0"（地图外）的
    ⇒ `UnitManager.PlaceUnit(unit, iX, iY)` 拉进城市**。不做快照比对、不删单位。
  * 触发：
    ① `Events.CityAddedToMap(ownerID, cityID, iX, iY)` ⇒ `HandleGhostCityAddedToMap`；
    ② `Events.CityTransfered(newOwnerID, cityID)` ⇒ `HandleGhostCityTransfered`（转城不一定触发 ①）；
    ③ 建城/转城函数末尾各调一次 `EnsureGhostSettlerInCity`（**幂等**：开拓者已在地图内就直接返回）。
    判据不再依赖池子/台账，而是"**这个玩家名下确实有地图外的开拓者**"（正常玩家不可能有）。
  * 日志（只在真的找到地图外开拓者时才打印，避免噪音）：
    `开拓者归位：player=… 扫描单位=N 地图外开拓者→城市=M 失败=0 位置=x,y 原因=… 明细=501@已入城`
  * **赠开拓者的机制已取消**（授权者 2026-10-17）：不再 `InitUnit` 补定居者，
    只把本来就存在的地图外开拓者移动进城市。因此也没有 `SpawnSettlerNear` 了。
  * 老存档兜底：载入后**第一次** `LocalPlayerTurnBegin` 跑一次 `SweepGhostOffMapSettlers`
    （已经有城、开拓者却还卡在地图外的存量档案，就地归位；Vassal System 侧不再自己整理）。

对外接口（都在 `ExposedMembers.ModMiscToolScript`）：
```

GetGhostOffMapSettlerCount(playerID)        → 其中在地图外（坐标 < 0）的个数
RelocateOffMapSettlersIntoCity(playerID, iX, iY, reason) → 拉进城市的个数（核心：遍历单位 → PlaceUnit）
EnsureGhostSettlerInCity(playerID, iX, iY, reason)       → 幂等版（没地图外开拓者就什么都不做）
HandleGhostCityAddedToMap(ownerID, cityID, iX, iY)       → 事件入口（内部用，通常不用自己调）
HandleGhostCityTransfered(newOwnerID, cityID)            → 转城事件入口（内部用）

```

**读档语义更正（重要）**：之前记的“过一个回合自动生效”指的是**外交效果**；
  **建立城市之后的实际效果仍然需要读档**。所以定制附庸的规则是：
  * 幽灵**当前身份已经相符**（`exactMatch`：当前文明+领袖都对）⇒ 不改身份 ⇒ 直接执行、免读档；
  * 否则要改身份 ⇒ 照旧“存档前配置、读档后执行”。
  批量城邦化本身**不需要读档**（它的效果就是城邦化后的外交表现 + 池子状态）。

—— 定制附庸的「完全匹配 ⇒ 跳过保存重读」契约（Vassal System 侧实现，2026-10-15 修正）——

背景：定制附庸要把一座城/一个开拓者交给幽灵玩家，如果目标幽灵的**领袖+文明**与玩家选的
      不一样，就得先改它的 PlayerConfigurations 身份，而身份改动要**存档 + 重读**才生效。
      所以 Vassal System 的 RequestCustomVassal 会先在幽灵池里找“领袖+文明完全匹配”的：
        * 完全匹配 ⇒ 不动身份 ⇒ 调用方可以直接执行，**跳过保存重读**；
        * 否则      ⇒ 存档前配置身份、写 pending，读档后确认再执行。
      返回值约定：(ok, err, exactMatch) —— 第三个值就是那个开关。

⚠️ **pcall 的返回值错位（就是这条功能一度没生效的原因）**：
    pcall(f, ...) 会**先塞一个自己的成功标志**，再排 f 的返回值：
        local ok, ret1, ret2, ret3 = pcall(f, ...)
    调用方原来写成 `local called, result, isImmediate = pcall(RequestCustomVassal, ...)`，
    于是 `isImmediate` 拿到的是 f 的**第二个**返回值（err=nil）⇒ 永远是 false ⇒
    “完全匹配直接执行”这条路一次都走不到（表现为：选中的领袖/文明明明和池里的幽灵一样，
    仍然弹“请存档再读档”）。现在改成
        local called, requestOk, requestErr, isImmediate = pcall(...)
    并在日志里打 `[VassalSystem][UI] 定制附庸请求：… immediate(领袖/文明已匹配，跳过保存重读)=true/false`。

GetPlayerSlotSummary()

### 2.7b 复制城邦（数据库扩容，可在创建游戏界面开关）

引擎能创建的城邦玩家数量 = **数据库里的城邦文明条数**（实测请求 62 只出 36）。
`GhostPlayers_CityStates.sql` 把每个城邦文明复制一份（类型名加 `_GHOST1`，
名称/类别/领袖/特质/城市名/配色全部照抄），可用城邦数量翻倍。

开关方式（参考 Atelier 的做法：**选项控制数据库加载**）：

* `GhostPlayers_Options.xml`（FrontEndActions）往 `Parameters` 表写一行 →
  创建游戏界面的“高级选项”里出现开关
  **「复制城邦以提供更多自定义玩家槽位」**（`ConfigurationId = MODMISC_DUPLICATE_CITY_STATES`，
  `DefaultValue="1"` 默认开启）；
* modinfo 的 `<ActionCriteria>` 用 `ConfigurationValueMatches` 读这个值；
* `GhostPlayers_CityStates.sql` 挂在 InGameActions 的 `<UpdateDatabase>` 上并带该判据 ——
  开关关闭时这个文件**完全不加载**，数据库保持原版状态；不设 LoadOrder，按默认顺序加载。

复制只针对 `StartingCivilizationLevelType = 'CIVILIZATION_LEVEL_CITY_STATE'` 的文明，
全部用 `INSERT ... SELECT` 从当前数据库取材，因此只影响原版的城邦，
场景/DLC 的城邦碰不到。涉及 7 张 gameplay 库的表：
`Types / Civilizations / TypeProperties / Leaders / CivilizationLeaders /
LeaderTraits / CityNames`。

**不要复制配色（PlayerColors）**——授权者实测结论，两个原因：

1. 配色属于**另一个数据库**（ColorManager），和 gameplay 库不互通，这个 SQL 文件里
   根本访问不到 `PlayerColors` 表（写了会报 no such table，加载直接失败）；
2. 就算换个文件复制进去，**相同 RGBA 值同时出场时，其中一方会回退到默认颜色**，反而更糟。

### 2.7c 复制城邦的图标（逐个定义）

图标属于独立数据库（IconManager），**没法用 SQL 批量拉取**（里面访问不到 `Civilizations`），
所以把 35 个原版城邦（含资料片、不含 DLC/场景）的图标逐条写死：复制体沿用原城邦
**同一张图集的同一个位置**（Atlas/Index 照抄），外观一致。

**格式用 XML 而不是 SQL**（`GhostPlayers_CityStateIcons.xml`）：与游戏自己的
`Icons_Civilizations.xml` 同一种写法，交给 XML 序列化器处理，既不依赖跨库查询，
也避开 SQL 侧 `Index` 这类保留字/方言坑。

**覆盖全部 41 个城邦，并且必须设 LoadOrder**：复制范围是“运行时数据库里已有的城邦”
（Base 24 + 资料片 11 + DLC 6 = 41，场景专属的不算），图标要与之一一对应。
复制体要引用原城邦的图集，而 **XP1/XP2/DLC 的图集（`ICON_ATLAS_EXPANSION_*`、
`ICON_ATLAS_VIKINGSLANDMARKS_*`）由官方图标动作加载**：本动作若排在它们前面，
引用会因“图集尚不存在”直接报数据库错，而且**报错会中断图标库构建**，
连后面本该加载的官方图标（例如 DLC 城邦 Palenque）一起丢掉。
因此 `<UpdateIcons>` 设 `LoadOrder=9000`，排在官方之后，图集齐了再引用。
（`GhostPlayers_CityStates.sql` 本身仍不设 LoadOrder。）

* 由同一个选项判据 `ModMisc_DuplicateCityStates_ON` 控制，挂在 `<UpdateIcons>` 上，不设 LoadOrder；
* `Icons` 行由 `IconDefinitions` 的触发器自动建，文件里再显式写一遍（`INSERT OR IGNORE`）以防万一，
  因此**重复执行是幂等的**；
* 坑：`Index` 是 SQLite 保留字，列名必须写成 `"Index"`（带双引号），否则整条语句语法错误。

### 2.8 跨存档数据自检（WriteCustomData / ReadCustomData）

> 每条接口“测过没有、结论是什么”，统一记在仓库根目录的
> **API_Verification_Status.md**（标注 `[已验证可用]` / `[已验证失败]` / `[部分可用]`）；
> 代码里对应的失败项也都带同名注释，改代码前先看那份清单。

用途：确认“创建游戏时写下的参数”能不能被之后的对局/读档读到（幽灵池的“玩家原本选择”
就靠它传递）。Civ6Common 里没有 SaveCustomData，写入统一走：

```lua
WriteCustomData(key, value)   -- 内部是 UI.GetGameParameters():Add(key, value)
ReadCustomData(key)           -- 读不到返回 nil
```

**探针**：放在 UI/Support_UI.lua 的启动函数 `Initialize()`（`Events.LoadGameViewStateDone`，
每次进入游戏只跑一次），**只输出日志**，不占面板：

1. 先 `ReadCustomData("ModMiscToolCrossSaveProbe")`；
2. 读不到 → 写入 `run=1;load=..;turn=..;prev=nil`；
3. 下次进游戏（或读档）若读到上次那份 ⇒ 跨存档成立。

日志里 `VERDICT=` 直接给结论：

| VERDICT | 含义 |
|---|---|
| `first-write` | 本次没读到 → 已写入第一份，需要再进一局才有结论 |
| `cross-save-OK` | 读到的是**上一次进游戏/另一个进程**写的数据 → **跨存档成立** |
| `same-session` | 读到的是**本次进游戏**里刚写的 → 只证明活过了这次读档，不算证据 |
| `FAILED ...` | 读写本身抛错（例如局内 `UI.GetGameParameters()` 不可写）→ 说明局内只能读不能写 |

payload 形如 `run=3;load=2;turn=0;prev=run=2;...`：`run` 每次进游戏 +1，`load` 是
“本进程第几次进游戏”，模块内用 `m_ProbeWrittenPayloads[payload] = loadIndex` 记账，
因此能区分“同一局里又读到自己刚写的”和“真的跨了局”。

两条测试路径：

* **跨局**：新建游戏 → 退回主菜单 → 再新建游戏；
* **跨进程**：新建游戏 → 存档 → 完全退出进程 → 重开 → 读档。

### 2.8a 高级选项溢出屏幕（安卓端）：结论 = **已撤回脚本适配，改为跳过高级选项**

> **2026-10-15 授权者实机：脚本适配没有生效**（`_PHONE` 后缀那套文件的界面脚本与布局都比较特殊），
> 因此本节的 `MODMISC_FIT_ADVANCED_OPTIONS` 适配代码**已从 `Civ6Common.lua` 里删除**，
> 同时**把 modinfo 里的高级选项整行撤掉**（`VassalDemand_Options.xml` 已删），
> 改为“跳过高级选项、主流幽灵申报数按地图尺寸取”（见 §2.8b）。下面保留的是当时的结构分析与评估记录。

（历史记录）可行性评估与当时的脚本修复方案

**现象**：创建游戏 → 高级选项里，加上本 mod 的选项后整块内容超出屏幕，底部（含本 mod 的
选项）点不到 ⇒ 不可用。授权者指出安卓端改不了游戏 XML。

**根因（按官方 XML 结构核对，与平台无关，是布局差异）**

| 变体 | 参数区容器 | 能否滚动 |
|---|---|---|
| 桌面 `AdvancedSetup.xml` | `<ScrollPanel ID="ParametersScrollPanel">` + `ScrollBar` | ✅ 能滚 |
| 手机 `AdvancedSetup_PHONE.xml` | `<Container ID="ParametersScrollPanel" Size="parent-8,parent-12">` | ❌ 普通容器，内容超高就溢出/被裁 |
| 平板 `AdvancedSetup_TABLET.xml` | 同上（Container） | ❌ 同样 |

另外：桌面 Lua 有 `Resize()` 按屏幕高度重算 `MainWindow` / `AdvancedOptionsWindow`；
**手机/平板 Lua 里那段被注释掉了**，窗口尺寸写死在 1920x1080 衬底上，矮屏更早溢出。

**纯脚本可行性：可行**（不需要改游戏 XML）。证据：
  * 我们的前端 hook 本来就跑在 `AdvancedSetup` 上下文里（`Civ6Common.lua` 取代版被该界面 include，
    这条路径在授权者机器上一直有效）⇒ `Controls` 是同一个上下文，够得着这些控件；
  * 需要的 API 全是基座自己用过的：`GetChildren()`（`GameSetupLogic_PHONE.lua` 第 598/613/621 行
    就是枚举 `PrimaryParametersStack` / `SecondaryParametersStack` 的）、`SetSizeY`、`SetFontSize`、
    `CalculateSize()`、`ReprocessAnchoring()`（本 mod 多处面板缩放也在用）。

（历史记录）**当时实现的脚本修复**（已于 2026-10-15 撤回；`_PHONE` 变体上未生效）
```lua
local MODMISC_FIT_ADVANCED_OPTIONS = true   -- 关掉它 = 完全不碰高级选项布局
local MODMISC_FIT_MIN_SCALE = 0.72          -- 行高/字号最多缩到 72%
local MODMISC_FIT_MAX_PASSES = 3
```
  1. **量**：`SecondaryParametersStack`（内容高）vs `ParametersScrollPanel`（视口高），先打日志；
  2. **压**：超了就按需要的比例缩参数行的行高 + 字号（下限 72% / 字号 ≥10），最多 3 轮；
  3. **兜底**：压到底仍不够时，按真实屏幕高度重算 `MainWindow` / `AdvancedOptionsWindow`
     （复刻桌面 `Resize()` 的意图；手机/平板没有 `LogoContainer`，所以只用 `ButtonStack` 那部分）。
  另外把选项名/说明也缩短了（`Text.xml` / `Text_CN.xml`），少占一行更好塞。

**测试协议**（授权者实机）
  1. 进创建游戏 → 高级选项，看日志：
     `[ModMiscTool][FitAdv] 高级选项：内容高=… 视口高=… 屏幕=…x… variantHint=PHONE/TABLET`
     —— 这一行直接给出“超了多少”。塞得下会打 `塞得下，不动布局`。
  2. 若日志显示压了 3 轮仍 `内容高 > 视口高`，把这两个数发我，调 `MODMISC_FIT_MIN_SCALE`
     或改走“去掉选项行 / 换 XML 取代”的路线（见下）。
  3. 不想让它碰布局：把开关改 false 即可（纯观测）。

**若脚本压不下去，还有两条备选**（都请授权者定）
  * **去掉选项行**：选项默认就是开启，取消它等于“总是申报 8+8”，行没了布局自然恢复原状（零布局风险，
    代价是不能再在界面上关掉）。
  * **XML 取代**：官方 DLC 正是用 `ImportFiles` 登记同名 XML 来替换界面
    （`Expansion2.modinfo` 的 `<ImportFiles id="Expansion2_Files">` 里就有
    `UI/Replacements/DiplomacyActionView.xml` 等），所以“把手机版参数区换成可滚动容器”在机制上成立；
    代价是要整份复制 `AdvancedSetup_PHONE.xml`（+平板版）并随官方更新维护，
    且**在授权者平台上 ImportFiles 换 XML 是否生效尚未验证**（换 Lua 是已验证的）。

### 2.8b 幽灵数量由声明方决定 + 城邦化（2026-10-15 授权者）

**分工**：`Mod Misc Tool` **只负责接受申报**（汇总 + 两道闸门），**数量由其它 mod 决定**。
默认声明方 = **Vassal System**（它的 `Vassal_GhostDemand.sql`），数量就写在那边。

**① 声明方（Vassal System）按地图尺寸声明数量 —— 走数据表**
```sql
-- Vassal System/Vassal_GhostDemand.sql（FrontEndActions → UpdateDatabase）：改数量只改这里
CREATE TABLE IF NOT EXISTS ModMiscGhostDemand (
    Source TEXT NOT NULL, MapSizeType TEXT NOT NULL,
    MajorGhosts INTEGER NOT NULL DEFAULT 0, CityStateGhosts INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (Source, MapSizeType));

DELETE FROM ModMiscGhostDemand WHERE Source = 'VassalSystem';
INSERT INTO ModMiscGhostDemand (Source, MapSizeType, MajorGhosts, CityStateGhosts) VALUES
    ('VassalSystem', 'MAPSIZE_DUEL',      4, 0),   -- 最小图 4 个主流幽灵
    ('VassalSystem', 'MAPSIZE_TINY',      8, 0),
    ('VassalSystem', 'MAPSIZE_SMALL',    12, 0),
    ('VassalSystem', 'MAPSIZE_STANDARD', 16, 0),
    ('VassalSystem', 'MAPSIZE_LARGE',    20, 0),
    ('VassalSystem', 'MAPSIZE_HUGE',     24, 0),   -- 最大图 24 个
    ('VassalSystem', '*',                12, 0);   -- 兜底行：尺寸认不出时
```

**为什么是数据表而不是让声明方在前端跑代码**：幽灵数量必须在“创建游戏”界面就定下来，
而消费者 mod 在**前端没有执行路径** —— 官方 modinfo 的 `FrontEndActions` 只允许
`AddMap / UpdateArt / UpdateColors / UpdateDatabase / UpdateIcons / UpdateText`
（没有任何能跑 Lua 的动作；`AddUserInterfaces` 在官方数据里只出现在 `InGameActions`）。
所以本框架把声明做成**数据契约**（谁都能用 `UpdateDatabase` 插行），而不是让框架去
`include` 别的 mod 的文件 —— 框架不依赖消费者，也不把别人的代码拖进自己的上下文。

**表结构契约**（框架建表，声明方 `CREATE TABLE IF NOT EXISTS` 后再插行，谁先跑都不会报错）
  * `Source` 声明方标识（同一个 Source 只取一条：有精确行用精确行，否则用 `'*'` 兜底行）
  * `MapSizeType` `'MAPSIZE_XXX'` 精确行 / `'*'` 兜底行
  * `MajorGhosts` 主流幽灵数（正常附庸行为池）；`CityStateGhosts` 城邦幽灵数（保守行为池，0 = 不产生）
  * 加声明方 = 自己插行（换个 `Source` 即可）；**没有行 = 该类幽灵 0**（框架自己不申报数量）。

**② Misc Tool 侧（接受方）**
  * 数据通道（默认）：每次刷新读声明表 —— 按**地图尺寸原始值缓存**，值没变就不重查
    （每帧成本 = 一次 `GetMapSize()` + 一次比较；表不存在只记一行日志并按 0 算）。
  * 动态通道（给能在前端跑代码的 mod，挂在 `ExposedMembers.ModMiscToolUI` 上）：
    `ModMiscToolRegisterGhostDemand(source, count)` / `...CityStateGhostDemand`（一次性）、
    `ModMiscToolRegisterGhostDemandProvider(source, fn)`（每次刷新调一次，返回 主流数, 城邦数）。
    同一个 `source` 后写的覆盖先写的；不同 source **相加**。
  * 汇总后生效值只受两个既有闸门限制：
    ① 幽灵总预算（该尺寸能多要多少城邦槽位，`GHOST_CITY_STATE_BY_MAP_SIZE`）；
    ② 槽位余量（`MaxPlayers` − 玩家自选主流 − 玩家自选城邦 − 城邦幽灵，防开局被挤爆）。
  * **本工具不 include 任何其它 mod 的文件**，也不自己申报数量。

**③ 桩验证**（`.harness/frontend_major_gradient_test.lua`：加载 Misc Tool 的真实前端 hook，
DB 桩按 Vassal System 的声明 SQL 喂行；自选 4 主流 + 6 城邦、`maxPlayers=62`）——**37 项全过**：
  * 六档 ⇒ 主流幽灵 **4/8/12/16/20/24**、参与玩家 **8/12/16/20/24/28**（城邦幽灵 0）✓
  * 声明表不存在 / 表里没有行 ⇒ 主流幽灵 **0**、参与玩家不变（硬规则）✓
  * 动态通道：同 `source` 覆盖表值（24 ⇒ 6）✓、异 `source` 相加（24 + 2 = 26）✓
  * 槽位不足（上限 10、自选 6+6）⇒ 夹到 **0** ✓；总预算 1（DUEL、城邦已 15）⇒ **1** ✓
  * 同局 SMALL→HUGE ⇒ **12→24**、参与玩家 16→28 ✓
  * 真机哈希路径（`GetValue("MapSize")`=nil ⇒ `GetMapSize()` 哈希）⇒ LARGE **20** / DUEL **4** ✓；
    之后每轮既不重算哈希也不重查声明表（都按原始尺寸值缓存）✓；尺寸完全认不出 ⇒ 兜底 **12** ✓

日志：
`[ModMiscTool][Ghost][DemandTable] 地图=MAPSIZE_HUGE 声明 1 条：VassalSystem major=24 city=0`
`[ModMiscTool][Ghost][MajorPlan] 地图=MAPSIZE_HUGE 申报=24 玩家自选 major=4 cityState=6 maxPlayers=62 总预算=56 ⇒ 主流幽灵=24 城邦幽灵=0 槽位余量=52`

**历史（都已撤）**：
  * 高级选项那一行在手机/平板布局下溢出屏幕 ⇒ modinfo 里整行删掉（§2.8a）。
  * 曾让本工具 include 声明方文件（`GHOST_DEMAND_PROVIDER_FILES`）——授权者否掉：
    框架不该依赖消费者、也不该把别人的代码拖进本上下文；改成现在的数据表 + ExposedMembers 两条路。
  * 压测期曾由本工具自己把主流幽灵**拉满到 52**（`GHOST_MAX_MAJOR_DEFAULT/CAP`），
    后又短暂改为“本工具按地图尺寸表申报”（`GHOST_MAJOR_DEMAND_BY_MAP_SIZE` 在 Misc Tool 里）——
    按授权者 2026-10-15 定论，**数量表移到声明方**，本工具只留接口与闸门。
    52 的结论保留为“引擎塞得下”，但常态按尺寸表走（小图 4 起步）。

⚠️ 申报方别把数量开太大：引擎要在地图生成阶段给这些玩家找出生点，塞不下会开局失败。

**④ 实机要核对的一行**：`[ModMiscTool][Ghost][DemandTable] 地图=… 声明 N 条：…`。
出现这行且条数/数值对 ⇒ 前端配置库里 `CREATE TABLE` + 插行 + 读表整条链通了；
若显示「声明表不可用（没装声明方或没建表）⇒ 本轮按 0 算」，说明前端配置库不接受建表
（或 Vassal System 的 SQL 没跑），那就退回“动态通道 + 前端补丁”路线（见上，需另验）。

**①b 城邦幽灵池默认未申报（0）**：它代表**保守附庸行为**（见 §2.7 末“两个池子 = 两种附庸行为”），
面板「外交压制自检」里城邦池显示 0 个 —— 预期状态，不是故障；
要测保守行为把声明方那边的 `GHOST_CITY_STATE_DEMAND` 改成 8（见 §2.8b ①）。

**①c 批量城邦化改为自动**：本地玩家**建立第一座城市**时自动执行一次（见 §2.7 末“自动城邦化”），
不需要手动点面板按钮（按钮仍保留，但**手动入口按 2026-10-17 定案拦截**，见 §2.8c-2）。

**② 面板两个压测按钮**（WorldBuilder 测试面板）
  * **「主流幽灵全部城邦化」** → `ConvertAllGhostMajorPlayersToCityState()`（面板按钮走手动入口，
    2026-10-26 起会被 §2.8c-2 的入口授权拦下；自动路径由 `TryAutoConvertGhostsOnFirstCity`
    传入 `'auto_first_city'`）：
    把池子里**仍在 off-map** 的主流幽灵逐个城邦化（已经有城市的会被顺手移出池子；
    已被带回地图使用中的跳过）。返回 `(converted, failed, skipped)`。
  * **「外交压制自检」**：把两类幽灵池里每个玩家的 `压制 / 可用 / 有城市` 逐条列出
    （压制判定用的就是外交 UI 那个入口 `IsDiplomacyGhostPlayerUI`），用来核对压测结果。

**③ 城邦化的实现契约**（`ConvertGhostPlayerToCityState(playerID[, civType[, conversionSource]])`）
  * 走 `WorldBuilder.PlayerManager():SetPlayerLeader(id, leader, civ, 'CIVILIZATION_LEVEL_CITY_STATE')`
    （与面板「应用」同一个接口）；**不调用 StartCityState()**（见 §10 第 29/31 条）。
  * 判定标准：转换后 `player:IsMajor()` 是否为 false；没变再补 `SetIsMinorCiv(true)` 配置标记。
  * 挑城邦文明时避开地图上已被占用的（避免重复城邦），全被占了就轮第一个并打日志。
  * **硬保护**：已经有城市的玩家直接拒绝（移除全部城市 = 玩家当场死亡）。
  * **时机**：只能在游戏跑起来之后执行；加载过渡阶段批量改身份会把开局搞挂。
  * **入口授权（2026-10-26 恢复 A 方案）**：`conversionSource = 'auto_first_city'`
    （本地玩家建首城自动批量）是唯一放行入口；不给来源 = 手动（面板 / 其它 mod）⇒ 按 §2.8c-2 拦截。
  * 注：2026-10-15 之前这个函数**从未被定义**（面板按钮与 `GHOST_CONVERT_MAJOR_TO_CITY_STATE`
    开关都指向 nil），这次一并补上了。

### 2.8c 城邦身份的硬规则：文明级 + 小文明原型领袖（2026-10-15 授权者报“官方城邦面板打不开”）

**硬规则**：任何被当作城邦的玩家（`player:IsMajor() == false`）必须同时满足
  ① 文明是城邦级（`Civilizations.StartingCivilizationLevelType = 'CIVILIZATION_LEVEL_CITY_STATE'`）；
  ② 领袖是**小文明原型**（`Leaders.InheritFrom` 非空：SCIENTIFIC / TRADE / CULTURAL / …）。

**为什么**：官方城邦面板 `Assets/UI/PartialScreens/CityStates.lua` 用领袖原型查加成文本 ——
原型查不到时 `GetBonusText` 只返回 `"UNKNOWN"`（第二个返回值 `Details` 为 nil），
而面板无条件拼接 `Bonuses[1].Title .. "[NEWLINE]" .. Bonuses[1].Details` ⇒ **拼接 nil 报错**
⇒ 整个城邦面板构建中断 ⇒ **启动栏的城邦按钮点了没反应**。

**我们这边的漏洞**：`ConvertGhostPlayerToCityState` 的兜底路径原来是“`ApplyPlayerConfigIdentity`
+ `SetIsMinorCiv(true)`”——如果领袖没换成小文明原型（`SetLeaderTypeName` 失败、
或 `SetPlayerLeader` 只改了文明等级没改领袖），就会留下**“城邦玩家 + 主流领袖”的半成品**，
正好踩上面那条 ⇒ 这次一并补上校验与修复。

**实现**（`ModTool_GhostPlayers.lua`，都是对外的 `ExposedMembers.ModMiscToolScript` 接口）
  * `IsLegalCityStateIdentity(playerID)` —— 身份是否合规（文明级 + 小文明原型领袖）。
  * `RepairCityStatePlayerIdentities()` —— 自检 + 修复：扫所有城邦玩家（跳过蛮族与自由城市），
    不合规的改写成合规城邦身份；改不成就如实计入失败并打日志。返回 `(合规, 修复, 失败)`。
  * `ConvertGhostPlayerToCityState` 现在**只在身份合规时才补 minor 标记**；转换后再校验一次，
    修不好宁可把 minor 标记撤回并返回失败（绝不留半成品）。
  * **进游戏时自动自检一次**（`ModTool.lua: Initialize` → `LoadGameViewStateDone` 之后，
    `pcall(RepairCityStatePlayerIdentities)`）——老存档里已经坏掉的身份会在读档后自动修好。
  * WorldBuilder 测试面板新按钮「修复城邦身份」（`WorldBuilderTestRepairCityState`）可手动补做，
    结果行 `LOC_MODMISC_WB_TEST_REPAIR_CITY_STATE_RESULT` 给出 合规/修复/失败 三个数。

**日志**：`[ModMiscTool][Ghost] 城邦身份自检：合规 N、修复 M、失败 K`；
修复过的每个玩家另打一行 `城邦身份已修复 player=… civ=… leader=…`（修复 0 就说明没有半成品身份，
城邦面板打不开就是别的原因 —— 这时要看 Lua.log 里 `CityStates` 相关报错）。

### 2.8c-2 主流→城邦：只放行"建首城自动批量"（2026-10-17 拦截 → 2026-10-26 恢复 A 方案）

**背景（2026-10-17 定案）**：把一个**主流玩家**造成城邦，引擎只会认下等级，
外交/使者那套数据不会跟着建 ⇒ 官方城邦面板取关系数据拿到 nil（行渲染报错、使者按钮失效），
玩家处于半城邦状态。城邦幽灵池本来就是在开局时由**真正的城邦**转过来的，不需要再做转换。

**2026-10-26 授权者恢复 A 方案**：只恢复**唯一验证过安全时机**的入口 —— 本地玩家
**建立第一座城市**时自动批量城邦化；其它入口仍然拦截：

* `ModTool_GhostPlayers.lua` 顶部：`GHOST_AUTO_CONVERT_ON_FIRST_CITY = true`（自动入口开）；
  `GHOST_ALLOW_MANUAL_MAJOR_TO_CITY_STATE = false`（手动入口关）；
  `GHOST_CONVERT_MAJOR_TO_CITY_STATE = false`（开局阶段那条仍关，实测会把开局加载搞挂）。
* 入口判定集中在 `IsMajorToCityStateConversionAllowed(conversionSource)`：只有
  `'auto_first_city'` 放行；`ConvertGhostPlayerToCityState` /
  `ConvertAllGhostMajorPlayersToCityState` 拿到别的来源（或 nil）一律拒绝并打日志
  `拒绝城邦化 player=…：入口=manual（主流→城邦只对"建首城自动批量"开放）`。
* `ConfigureGhostPlayerIdentity` 仍拒绝把主流玩家下发成 `CIVILIZATION_LEVEL_CITY_STATE`
  （Vassal System 的定制附庸走这条）。
* 已经见过面的幽灵照旧跳过（§2.8c 的硬规则没有变化）。
* 日志核对：模块加载行
  `autoCityStateConvert=false autoConvertOnFirstCity=true manualConvert=false`；
  首城那一刻 `本地玩家建立第一座城 ⇒ 自动批量城邦化（… 入口=auto_first_city）`，
  随后 `首城自动城邦化结果：converted=… failed=… skipped=…`。
  全失败时**不落**“已完成”标记，下一座城会再试一次。

**面板过滤（豁免型）**：`CityStates_ModMiscGhost.lua` 仍然把"主流转出来的城邦"从官方列表里摘掉
（隐形占位，避免基座崩溃），但**城邦幽灵池出身的一律豁免、照常显示**：

| 原身份台账 | 处理 |
|---|---|

判定用 Misc Tool 存档里的"原身份台账"（`GetGhostOriginalIdentity`），随存档走、不依赖运行时状态。
桩测试：`Basilissa Mod Misc Tools/.harness/citystates_patch_test.lua`（含三条豁免/摘除用例）。

### 2.8d 城邦面板打不开会把回合卡死 —— 自愈（2026-10-15 授权者定位）

**链路（全部核对过基座代码）**
  1. 给城邦派使者是**回合拦截项**：`ActionPanel` 的 `ENDTURN_BLOCKING_GIVE_INFLUENCE_TOKEN`
     （拦截消息点下去 → `ActionPanel:DoEndTurn` → `LuaEvents.ActionPanel_ActivateNotification`）。
  2. `Panels/NotificationPanel.lua` 的 `OnGiveInfluenceTokenActivate` →
     `LuaEvents.NotificationPanel_OpenCityStatesSendEnvoys`；
     启动栏入口则是 `LaunchBar_PHONE.lua: OnCityStates` → `LuaEvents.LaunchBar_OpenCityStates`。
  3. 面板本体 = **PartialScreens/CityStates**（`_PHONE` 变体同名）。
  4. `InGame.lua: BulkHide(isHide, who)` 隐藏/显示的是**五大组**：
     `WorldViewControls / HUD / PartialScreens / Screens / TopLevelHUD` ——
     `/InGame/PartialScreens` **正是城邦面板所在的那一组**，而且是**引用计数**
     （`m_bulkHideTracker`）。

**后果**：只要有界面调过 `BulkHide(true, "Diplomacy")`（外交界面 `InitializeView` 里那对
`DiplomacyActionView_HideIngameUI/ShowIngameUI`，同时还会 `Input.PushActiveContext(Diplomacy)`）
而配对的 show 没跑到，城邦面板就**永远显示不出来**（父组隐藏时子控件的 `SetHide(false)` 无效）
⇒ 使者派不出去 ⇒ **玩家无法进入下一回合**。本 mod 挡下幽灵的外交入口时就可能留下这种半开状态。

**自愈**（`UI/Support_UI.lua`，导出到 `ExposedMembers.ModMiscToolUI`）
  * `AreInGameGroupsHidden()` / `IsDiplomacyInputContextActive()` —— 两个判据。
  * `PairDiplomacyBulkShow()` —— fire 原版 `LuaEvents.DiplomacyActionView_ShowIngameUI`，
    让 `InGame` 自己执行 `BulkHide(false,"Diplomacy") + Input.PopContext()`（保持引用计数配平）；
    事件不可用才退回手动 `Input.PopContext()`（且只在确认卡着外交上下文时）。
  * `HealInGameUIForPanelOpen(why)` —— 上面两条判据任一命中就修（隐藏组 → 强制显示；
    外交输入上下文卡住 → 配平）。
  * **触发点只有两个**：`LuaEvents.LaunchBar_OpenCityStates`（启动栏按钮）与
    `LuaEvents.NotificationPanel_OpenCityStatesSendEnvoys`（回合拦截那条路）。
    只在这两个“城邦面板要被打开”的时刻做，避免误伤全屏地图/外交界面这类**合法隐藏**。
  * 面板里的「恢复 UI」按钮仍然保留（手动兜底）。

**“点不动”的真正机制（2026-10-15 实机日志定案）**
  1. `InGame_PHONE.xml` 里城邦上下文是 `<LuaContext ID="CityStates" FileName="CityStates" Hidden="1" />`
     —— **注册即隐藏**；
  2. 只有 `OpenOverview()` / `OnOpenSendEnvoys()` 的**最后一行** `m_kScreenSlideAnim.Show()`
     会调 `ContextPtr:SetHide(false)`（`AnimSidePanelSupport.lua:37-40`）；
  3. 所以 `Refresh()` 里**任何一行抛错** ⇒ `Show()` 跑不到 ⇒ 面板不显示，而且每次点击重演同一个错
     ⇒ **永久“点不动”**；而城邦面板是“给城邦派使者”这个回合拦截项的出口 ⇒ 回合卡死。
  实机日志对上了：`AddCityStateRow → GetRelationshipPipAtlasPieces(380) →
  DIPLO_PIP_INFO[kCityState.DiplomaticState].IconName`，某玩家外交状态 -1 ⇒ 索引 nil；
  而且它在**上下文加载阶段**就炸（`Initialize → Refresh → ViewList → AddCityStateRow`），
  日志里跟着一行 `Error loading file where=…CityStates_Expansion1.lua:9`。
  ⇒ 因此**只包 AddCityStateRow 不够**（加载期那次调用发生在我们的包装装上之前）。

**面板本体加固（官方 ReplaceUIScript 补丁，与外交两处同一套做法）**
  * 文件：`UI/Replacements/CityStates_ModMiscGhost.lua`；登记：`<LuaContext>CityStates</LuaContext>`
    的 `<ReplaceUIScript>`（LoadOrder 1000）；层链 `XP2 → XP1 → 基座`
    （`ModMiscToolIncludeUILayer("CityStates", "CityStates_Expansion1.lua", "CityStates_Expansion2.lua")`）。
  * ① 覆盖 `GetBonusText`：`Details`/`Title` 为 nil 时补空串 ——
    基座面板行的崩溃点就是 `Bonuses[n].Details` 为 nil（非法城邦身份 = 领袖没有
    `InheritFrom` 时 `GetBonusText` 只返回 `"UNKNOWN"`）。
  * ② 包一层 `AddCityStateRow`：单行数据出错只跳过该行并打日志，不再让整个面板构建中断。
  * ②b **返回值必须原样透传**：基座 `ViewList` 是
    `local kInst :table = AddCityStateRow( kCityState )`，游戏 Lua 会**运行时检查**这个 `:table`
    注解 —— 兜底函数返回布尔/nil 会抛
    `Type check failed: (expected 'table', but got 'boolean')` 并**掐断整个列表循环**
    （实机表现：只渲染 1 行、另一个已发现的城邦整行消失）。所以：好行 `return kInst`，
    坏行 `return {}`（空表，保证类型检查过得去、后续行照常）。
  * ③ **包一层 `Refresh`（命门）**：整体 pcall —— 保证调用方还能走到 `Show()` 把面板弹出来；
    并在每次刷新后打一行 `本轮列表：渲染 N 行、跳过 M 行`（用来回答“游戏里有 2 个城邦、
    面板里怎么只有 1 个”：N 少于城邦数 ⇒ 那些城邦根本不在 `PlayerManager.GetAliveMinors()`
    里，是引擎侧/地图侧的状态问题；M>0 ⇒ 我们的行构造仍然渲染不出来，日志里有原因）。
  * ④ 打开入口包装 + 重新登记：`PartialScreenHooks_OpenCityStates` 与
    `NotificationPanel_OpenCityStatesSendEnvoys` 原版登记的是**函数引用**，重定义全局不影响它，
    所以补丁显式 `Remove` 旧引用再 `Add` 包装版；每次打开打一行
    `[ModMiscTool][CityStates] 打开面板入口=… 进来时上下文隐藏=…`（下次排查一眼可判），
    并顺手把上下文 `SetHide(false)` 作为最后保险。
  * 缓存名用 `MODMISC_BASE_` 前缀：官方 XP1 自己把上一层缓存成 `BASE_AddCityStateRow`
    并在调用时读它，用官方前缀会自读自 ⇒ 无限递归（本项目既定约定）。
  * 桩验证 `.harness/citystates_patch_test.lua`（13 项全过）：先复现“坏领袖 ⇒ Details=nil ⇒
    行构造抛错”，再验证补丁后 Details 一定是字符串、坏行只被跳过且有日志；
    还模拟“`Refresh` 抛错 + 上下文隐藏”的状态机，验证**两个入口（面板按钮 / 派使者回合拦截）
    都不再抛错、并且上下文被 unhide（面板确实弹出来）**。

**日志**：命中自愈时打
`[ModMiscTool][RestoreUI] <why>：检测到界面被隐藏/输入上下文卡住（… ，外交输入=…），开始自愈`
与 `[ModMiscTool][RestoreUI] 已补齐原版配对：DiplomacyActionView_ShowIngameUI`
`[ModMiscTool][RestoreUI] 已恢复：PartialScreens,…`；
若这三行都没出现而面板仍打不开，请看 Lua.log 里基座自己打的
`Request to BulkHide( … )` 与 `Runtime Error`（那时问题在别处，不在隐藏状态）。

### 2.8e 见面过的幽灵必须留在主流体系（2026-10-15 授权者定位 + 实机日志确认）

**实机日志给出的三条硬证据**（Lua.log，2026-10-15 22:16 那份）
  1. `CityStates: [ModMiscTool][CityStates] 跳过一行坏数据 player=6：
     zip:Base/Assets/UI/PartialScreens/CityStates_PHONE.lua:380: attempt to index a nil value`
     —— 崩溃点是 `GetRelationshipPipAtlasPieces` 里的
     `DIPLO_PIP_INFO[kCityState.DiplomaticState].IconName`：该玩家的外交状态是 `-1`
     ⇒ `DiplomaticState = nil` ⇒ 索引 nil ⇒ 面板构建中断。**面板本体加固补丁正好接住了它**
     （§2.8d 的两条兜底），所以现在面板行不会再把整个面板带崩。
  2. `城邦身份自检：合规 14、修复 0、失败 44（18…61 identity still illegal after apply）`
     —— 这 44 个其实是**空槽位**（`applied player config … civ=nil leader=nil level=0`）：
     引擎没给这些槽位建玩家，`IsMajor()` 也返回 false。**自检已改为跳过空槽位**
     （`civType == nil or ''`），不再误报“失败”。
  3. 该局 `autoCityStateConvert=false`（自动城邦化没开）⇒ 那些城邦化是**手动面板按钮**触发的，
     所以“见面过的幽灵被转成城邦”是可以人为造成的，必须在转换入口上就挡掉。
     （2026-10-26 起首城自动路径已恢复；手动入口仍关，见 §2.8c-2。）

**结论（授权者定的语义）**：**已经和本地玩家见过面的幽灵不许进/留在城邦体系** ——
  见了面就进了外交关系数据，转成城邦后官方城邦面板取不到关系透镜数据 ⇒ 面板打不开 ⇒
  “给城邦派使者”这个**回合拦截项**卡死 ⇒ 玩家无法进入下一回合。

**实现（三层，规则只在第一层判定）**
  * **① 源头过滤（主手段，唯一判定层）**：`ConfigureGhostPlayerIdentity` —— 这是**所有改身份的收口**
    （Misc Tool 面板、Vassal System 的定制附庸都走它）。当目标等级是
    `CIVILIZATION_LEVEL_CITY_STATE`、且该玩家当前是主流、且本地玩家**已经见过**它 ⇒ 直接拒绝并打日志
    `拒绝把已见面的玩家转成城邦：player=…（见面幽灵留在主流体系）`。
    `ConvertGhostPlayerToCityState` 与批量入口 `ConvertAllGhostMajorPlayersToCityState`
    另做了同样的检查（更早报错、批量入口计入 `skipped`）。
  * **② UI 兜底（不承担规则）**：城邦面板加固补丁（`CityStates_ModMiscGhost.lua`）+ 界面自愈
    （`HealInGameUIForPanelOpen`）—— 即使某天又出现坏数据，官方城邦面板也不会因此打不开。
  * **③ 补救入口**：面板按钮「见面的幽灵转回主流」`RestoreMetGhostsAsMajorPlayers()`。
  * `LocalPlayerHasMet(playerID)`（全局，已导出）—— 包装 `localPlayer:GetDiplomacy():HasMet(id)`。
  * `ConvertGhostPlayerToCityState`：**开头就检查**，见面过的直接拒绝并打日志
    （`本地玩家已经见过它（见面幽灵留在主流体系）`）；批量入口
    `ConvertAllGhostMajorPlayersToCityState` 也先过滤并计入 `skipped`。
  * `RestoreMetGhostsAsMajorPlayers()` —— 把台账里**已经见面**的幽灵用**进池子时记的原身份**
    （`GetGhostOriginalIdentity`）转回主流（`CIVILIZATION_LEVEL_FULL_CIV`：`SetMajorCiv()` +
    `SetIsMinorCiv(false)`）；返回 `(恢复, 本来就是主流, 失败)`。
    ⚠️ 只挂在**面板按钮**上（WorldBuilder 测试面板「见面的幽灵转回主流」，
    `WorldBuilderTestRestoreMetGhosts`）—— 批量改身份**不能在开局加载阶段做**
    （实机撞过：加载会被中止），按钮触发后按流程存档重读。

### 2.9 UI 脚本改动方式：Civ6Common 保持取代 + 外交两处用官方 ReplaceUIScript 补丁

【2026-10-15 授权者定】分两类处理，**不再一律整体复制，也不一律改补丁**：

**① Civ6Common.lua —— 保持整体取代不变**（`ImportFiles` + LoadOrder 10000，前端与对局内各登记一次）
它承担两件事，且都已实机验证过，所以不动：
  * 对局内：移动拦截（`MoveUnitToPlot`，这个函数就定义在 Civ6Common 里）；
  * 前端：建局 hook（拉上限 / 按 mod 申报量分账 / 玩家选择写随档）与地图尺寸解析
    （`ModMiscToolResolveMapSizeKey` 导出给 `UI/ModMiscCreateGame.lua` 的换图指纹用）。
  * 它是“支持文件”不是 UI 上下文，本来也没法用 `ReplaceUIScript`。

**② 外交两处 —— 改成官方 Expansion1/2 那种 `ReplaceUIScript` 补丁**
（样板：`Civ6Data/Expansion1|2/UI/Replacements/*_Expansion*.lua` +
官方 modinfo 里的 `<ReplaceUIScript>`：`include` 上一层脚本 → 缓存上一层函数 → 只覆盖要改的）

| 补丁文件（UI/Replacements/） | LuaContext | 改了什么 |
|---|---|---|
| `ModMiscGhostShared.lua` | （被 include） | 资料片判定、按链 include 上一层、幽灵判定（外交两处共用） |
| `DiplomacyRibbon_ModMiscGhost.lua` | `DiplomacyRibbon` | 覆盖 `AddLeader`：幽灵不进外交条 |
| `DiplomacyActionView_ModMiscGhost.lua` | `DiplomacyActionView` | 覆盖 `OnDiplomacyStatement` + 套 `TestValid` + 覆盖 `SelectPlayer`：幽灵不弹领袖窗、也不可被选中 |

资料片链：`ModMiscToolIncludeUILayer(context, xp1File, xp2File)` 按数据库探针
（`GameInfo.Governors` ⇒ XP1；`GameInfo.CoastalLowlands` ⇒ XP2，按官方 Schema 核对过）
接到**当前生效那一层**后面：XP2 → XP1 → 基座。日志：
`[ModMiscTool][UILayer] <context> <- include(<实际那一层>)  xp1=.. xp2=..`。

**两条硬规矩**（都是本轮踩出来的）：
  1. 缓存上一层函数用 `MODMISC_BASE_<函数名>`，**不要**用官方的 `BASE_<函数名>` ——
     官方补丁正是用这个名字缓存上一层，而且是在**调用时读全局**；同名会被我们顶掉并自递归。
  2. 被 `include("<名字>")` 加载的文件必须登记在对应阶段的 `ImportFiles`
     （只写 `<Files>` 不够，那是打包清单）。本 mod 里 `ModMiscGhostShared.lua`
     登记在 `InGameActions → Imports`。

实机核对日志：`[ModMiscTool][UILayer] ...`、`[ModMiscTool][Ghost] 外交弹窗闸门已装载`、
以及原来那两条（前端 `setup hook installed`、对局内 `MoveUnitToPlot` 相关）。

### 2.9b 【2026-10-15 授权者】UI 改动与“新版游戏文件”的兼容性核对

问题：mod 里对 UI 的改动，和 Civ6PC 里的新版官方文件是否兼容？

结论（按两套官方文件实测比对：`Civ6Data` = 手机/Aspyr 版，`Civ6PC` = PC 版）：

| 我们的改动 | 机制 | 新版兼容性 |
|---|---|---|
| `DiplomacyRibbon_ModMiscGhost.lua` | `ReplaceUIScript` + `include` 当前层 + 覆盖 `AddLeader` | ✅ **跟版本走**：只按名字覆盖，`AddLeader` 在手机版（含 `_PHONE`）与 PC 版里都存在（baseline 核对过）；新版权改了别的函数不影响我们 |
| `DiplomacyActionView_ModMiscGhost.lua` | 同上，覆盖 `OnDiplomacyStatement` / `TestValid` / `SelectPlayer` / `OnOpenDiplomacyActionView` | ✅ 四个目标函数在两套基座的桌面版与手机版里都存在；`SelectPlayer`/`OnOpenDiplomacyActionView` 连函数体都一致，只有 `OnDiplomacyStatement` 因平台差异不同（我们不复制它，只包一层） |
| `ModMiscGhostShared.lua` | 资料片判定 + 平台链 include | ✅ 与游戏版本无关（判据是数据库表） |
| `UI/Replacements/Civ6Common.lua`（整体取代） | `ImportFiles` 同名替换 | ⚠️ **版本绑定**：它是**手机/Aspyr 基座**的副本（含 `-- ASPYR --` 段；PC 基座没有这些），所以：① 在手机版上正确；② 官方更新后必须重新同步（把新基座拷过来再贴回我们的两处钩子）；③ 直接拿到 **PC 版**上用会把手机分支的逻辑带进去。函数覆盖面上是 PC 的超集（PC 独有函数 = 0），所以不会缺函数，但“平台行为”会串。 |

顺带记两条实测经验（本次一起确认的）：
  * `include("X")` 与 `LuaReplace` 都是**平台感知**的：手机版上 `include("DiplomacyActionView")`
    会取 `DiplomacyActionView_PHONE.lua`（官方 `ActionPanel_Expansion1_PHONE.lua` 也这么写），
    所以补丁**不需要**再补一份 `_PHONE` 孪生文件；我们的两个外交补丁在授权者机器上生效即此证据。
  * `Civ6Common.lua` **没有** `_PHONE` 变体（两套基座都只有一份），所以整体取代它在所有
    平台变体里都能生效 —— 这也是它至今仍是“整体取代”的原因之一。

### 3.9 跨存档存储（ModMiscStore）
------------------------------------------------------------------------------

原版**没有**可用的跨存档存储 —— 已逐条实测排除：CustomData 不落盘、配置档也不带它、
对局内读配置档直接卡死、io 库不存在（`io=n io.open=n`）、`Options.SetUserOption`
拒绝未注册的键、存档元数据字段全由引擎填。

本 mod 的做法：把数据**编进配置档的文件名**，下一轮启动从存档列表读回。
两端都是原版接口 —— 写 `Network.SaveGame{Name=…, FileType=GAME_CONFIGURATION}`、
读 `UI.QuerySaveGameList` 的 `Name`（都不需要读档）。
实机验证：写一轮 → 杀进程 → 下一轮读回，payload **逐字一致**；前端与对局内 UI 都能读写。

规范：
* 文件命名 `ModMiscStore~<hex(key)>~<hex(value)>.Civ6Cfg`，一个 key 一个档；
  值 ≤ 120 字节。hex 是为了绕开文件名禁用字符（`% " < > | / \ * ? :` 与控制字符）。
* 写：先写新档，收到 `Events.SaveComplete` 后再删同一个 key 的旧档（写失败不丢数据）。
* 读：扫一遍配置档列表，按 key 去重（同名档留修改时间最新的那份，其余清理）。
* 只能存**字符串**；表/数字请自行序列化。

接口（`ExposedMembers.ModMiscToolUI.*`，前端与对局内 UI 两个 context 各挂一份）：

    RefreshData()                 扫存档列表（异步）
    IsDataReady()                 首次扫描是否已完成
    OnDataReady(fn)               扫描完成时回调（已就绪则立刻调用）
    SaveData(key, value)          写；返回是否已发出请求（落盘是异步的）
    GetData(key)                  读（没存过 → nil）
    GetAllData()                  整张表（副本）
    RemoveData(key)               删一个键及其档
    RemoveAllData()               清空整张存储（返回删掉的键数）

典型用法：

    local api = ExposedMembers.ModMiscToolUI
    api.OnDataReady(function()
        local settings = api.GetData("my_mod_settings")
        -- ... 用完之后
        api.SaveData("my_mod_settings", "version=2;volume=7")
    end)
    api.RefreshData()

注意：
* **数据本体就在文件名里**（`ModMiscStore~<hex(key)>~<hex(value)>.Civ6Cfg`）：写的是**配置档**，
  读靠列目录解码文件名 —— **不需要新生成普通存档、也不需要加载任何档**；
  改写 = 写新文件 + 删旧文件（`UI.DeleteSavedGame`）。代价是一个 key 留一个小档，适合少量短数据。
* 数据存在 **UI 层**（`Network.SaveGame` / `UI.QuerySaveGameList` 都是 UI 接口），
  gameplay 侧拿不到；需要在 gameplay 用，就经 `ExposedMembers` 转一手。
* 每次写入都会在玩家的**载入配置**列表里留下一个档（一个 key 一个），
  这是这条通道的固有代价；`RemoveData` / `RemoveAllData` 可随时清理。
* 存储档的名字是编码过的 hex，玩家在列表里看到的是乱码 —— 建议只存少量键值。

### 3.10 AssetPreview 资产预览 / 永久资产放置（ModMiscAssetStore）
------------------------------------------------------------------------------

#### 3.10.1 引擎自带的 AssetPreview（只影响画面，不进存档）

`AssetPreview` 是引擎在 **UI 层**提供的全局对象，用来在任意地块上“摆”出资产模型
（城市 / 区域底座 / 建筑 / 地标 / 单位）。它**纯视觉**：不改变游戏状态、不属于存档，
**存档再读回来就没了**。原版自己也在用（`Automation_Profile.lua` 拿它铺满地图做跑分）。

常用调用（全部 UI 层）：

    AssetPreview.SpoofCityAt(x, y, civIndex, eraIndex, 22)
    AssetPreview.SpoofDistrictBaseAt(x, y, civ, era, appeal, 0, "Worked", districtIndex, variantIndex)
    AssetPreview.SpoofBuildingAt(x, y, civ, era, appeal, "Worked", districtIndex, buildingHash)
    AssetPreview.SpoofLandmarkAt(x, y, civ, era, appeal, resourceHash, "Worked", landmarkIndex, variant)
    AssetPreview.SpoofUnitAt(x, y, cultureHash, unitHash)

    AssetPreview.ClearLandmarkAt(x, y)   AssetPreview.DestroyAt(x, y)
    AssetPreview.ClearLandmarkSystem()   AssetPreview.ClearUnitSystem()   AssetPreview.DestroyAll()

#### 3.10.2 本 mod 的永久放置（落入存档、读档自动重放）

因为预览不进存档，本 mod 把**已经解析好的调用**记进 CustomData（随普通存档序列化、
读档还原），开局时重放。记录的是 `{ fn = "SpoofCityAt", args = {…} }` 这种调用规格，
而不是“选中了哪个资产”——这样读档时不必再查资产库，也不会因索引变化放错。

接口（`ExposedMembers.ModMiscToolUI.*`）：

    PlaceAssetPersistent(fnName, args)   放置 + 记录 + 落 CustomData（args 是数组 {x, y, …}）
    RemovePersistentAssetsAt(x, y)       删掉该地块的记录（只动记录，不动画面）
    ClearPersistentAssets()              清空记录（返回清掉的条数）
    RestorePersistentAssets()            按记录重放（读档时已自动重放一次）
    GetPersistentAssetCount()            记录条数
    GetPersistentAssets()                记录副本

注意：
* **顺序很重要**：CustomData 记的是**存档那一刻**的快照 —— 要“永久”就得
  **先放置、再存档**；存档之后再放的，读档时不会出现。
* 重放只在 `Support_UI` 里触发一次（模块本身不挂事件，免得每个 context 各重放一遍）。
* 测试面板上的「放置资产 / 清除地块资产 / 清除全部资产」已经接了这套，
  另有「重放放置」按钮可手动触发一次重放。

#### 3.11.3 证据链（怎么判断调用之后到底进了哪一局）

`ArmMarker` 把「调用前的快照」写进 `cg_marker`（协议 persave 表，UI 侧 CustomData）；
随档数据 **随局随档、新局不继承**
（已验证），于是：

* 标记**读不到** → 现在这局是**新建的**；
* 标记**读得到** → 还是原来那局（调用是空操作），或读回了存档之后的旧档；
* 新局指纹里的 `script=` / `grid=` 和目标值一致 → **换图成功**；还是原值 → 建了新局但没换图。

结论全部打在 Lua.log，前缀 `[ModMiscTool][CreateGame]`，涉及的关键行：

    api: …                   各接口是否存在（y/n）
    routes: …                改图四条路径的可用性
    now: turn=…;script=…;size=…;grid=…;players=…
    marker armed: [act=…;nonce=…;t=…;…]
    即将调用 … / 调用已返回（没卡死）
    after-create: VERDICT=new-game | marker-present

#### 3.11.4 实机结论（2026-10-05）

* `Network.RestartGame()` —— **对局内可用**：立刻重开一局，地图**重新生成、换种子**，
  但**地图脚本不变**（对局内写的 `MAP_SCRIPT` 不被采纳：RestartGame 用的是“开局前那份配置”，
  见 `InGameTopOptionsMenu.lua:317`）。
* `Events.SetGameEntryMethod` + `Network.HostGame(SERVER_TYPE_NONE)` —— **对局内不可用**：
  调用返回、进程不崩，但**不建新局**（静默空操作）。面板按钮与 `HostGameInGame` 已移除。
  想换**地图脚本**只能退主菜单、在创建游戏界面重新开局。
* 前端探针 `[ModMiscTool][MapConfigProbe]`（在 `UI/Replacements/Civ6Common.lua`）：
  在创建游戏界面打一行当前配置（`MAP_SCRIPT` / `MAP_SIZE` / `SEED` / `START_ERA` / `START_TURN`）。
  **实机结论（2026-10-05）：退回主菜单后打出来的还是原来那张图** ⇒ 配置在离开对局时就被重置，
  「退主菜单再创建」也带不走对局内写的 `MAP_SCRIPT`；**换地图脚本彻底没有就地办法**。
  探针保留（只在值变化时打一行），以后再遇到“配置到底有没有传过去”的问题可直接看它。

#### 3.11.5 注意

* 三个入口（`RestartGame` / `ExitToMainMenu`）都会**把当前局顶掉或直接重开**，
  想保住进度先点「切换前存档」（普通档，档名 `ModMiscCreateGame~switch-backup`）；
* 对局内改配置是**直接写配置对象**，绕过了前端 SetupParameters 的参数系统，
  所以前端那套“游戏已开始不可改”的限制在这里不适用 —— 但**写了算不算数要实测**
  （RestartGame 用的是“开局前那份配置”，可能忽略对局内的改动；HostGame 读当前配置）；
* 引擎自带的 Automation 明确要求 `HostGame` 站在主菜单才能用
  （`Automation_StandardTests.lua:489`）⇒ 对局内直调**实测确实无效**（见 3.11.4）；
* 每次进游戏（新局 / 读档）都会打一行开局探针结论，属正常日志，不是报错。

### 3.13 存档关系与换图（ModMiscSaveGraph / ModMiscSavePanel，**成品功能**）
------------------------------------------------------------------------------

**做什么**：给“换地图”这个功能配一套存档机制 —— 换图前先存原档，并把存档之间的
**主线 / 分支**关系记下来，让玩家看得见“哪一档是本线的最新进度、哪一档是从哪儿分出来的”。

**为什么这么设计**（前置结论都来自实机，见 `API_Verification_Status.md` 第 12 节）：

* 对局内**换地图脚本没有任何办法**：写 `MAP_SCRIPT` 既不进重开，也活不到前端；
* 唯一能换的是**同一地图脚本重新生成（换种子）**，靠 `Network.RestartGame()`；
* 重开 = 丢掉当前世界 ⇒ **必须先存档**，而且这份原档要能找回来；
* 跨存档唯一可用通道是**存档文件名**（通道 C）⇒ 关系信息写在档名里；
* 随档数据（UI 侧 CustomData / gameplay 侧 SetProperty）**不跨新局** ⇒ 节点身份用随档身份
  `sgnode`（协议 persave 通道）带，换图后的父子关系用存储通道带。

#### 3.13.1 档名格式（**不可随意改**，解析全靠它）

    MMT~<id>~<parent>~<kind>~T<turn>~<map>~<stamp>
    例：MMT~m4k2x1az~0~M~T042~Pangaea~20261005-1432

| 字段 | 含义 |
|---|---|
| `id` | 本档编号：base36 时间戳 + 2 位随机（唯一、可排序） |
| `parent` | 父档 id；`0` = 树根（第一档，或接手没有记录的局） |
| `kind` | `M` 主线（延续当前主线头）／`B` 分支（从非主线头分叉：SL 试验、换图后的新局） |
| `turn` / `map` / `stamp` | 存这一档时的回合 / 地图脚本名 / 时间，给人看 |

文件名禁用字符（`% " < > | / \ * ? :`）与分隔符 `~` 一律替换成 `_`。
**游戏自带存档菜单存的档不带这个格式，不会进这棵树** —— 玩家为 SL 随便存多少档都不会污染关系树。

#### 3.13.2 主线 / 分支怎么自动判（只给一个存档按钮）

* 当前节点 == **主线头**（存储键 `sg_head`）→ `M`：这是本线的最新进度；
* 当前节点不是主线头（例如读了一档旧档继续玩 = SL）→ `B`：它从主线分叉出去；
* 没有当前节点（新局第一次存档）→ 有“待接分支”就接它（换图后的新局），否则当树根。

每次写出 `M` 档就把主线头推进到它；`B` 档不动主线头。**当前节点**来自随档身份 `sgnode`
（协议 persave 通道；UI 侧 CustomData）
（`ModMiscSaveGraph_NodeId` 等）⇒ 读档进游戏就知道自己在哪个节点。

#### 3.13.3 换图流程（面板上一个按钮）

    「换图（先存原档）」：
      ① 先算好新节点并**先写“待接分支”**（存储键 sg_pending = `<原档id>|B|<stamp>`）
         —— 重开后只有存储通道能把关系带过去，先写就给了它落盘时间；
      ② 存原档（按 3.13.2 自动判 M/B，主线上就是 M）；
      ③ 等 SaveComplete → 复查存档列表确认原档落盘 → Refresh 存储确认 pending 落盘；
      ④ Network.RestartGame()；
      ⑤ 新局进游戏 → 开局探针读到待接分支：本局第一次存档自动挂到原档下、算**分支**，
         pending 随即消费掉；之后在本局继续存 = 这条分支的延续。

失败兜底：`pending` 两次都没确认也照样重开（原档已保存，丢的只是一条边，不损坏任何档），
日志里会写清楚。

#### 3.13.3b 换图 = 两步式（2026-10-05 **实机验证通过**）

> 实机日志（第 14.2f 节）确认：两步式换图 + 分支关系 + 落盘复查 + 新局接手，全链路跑通。
> 同时修掉一个隐藏 bug：`ModTool.lua` 暴露 `ModMiscToolData` 却没 include `ModTool_DataStore.lua`，
> 报 `attempt to index a nil value` 后**中断了整个 Initialize**，导致 `Game:SetProperty` 通道与
> `WorldBuilderAPI` / `TurnEraAPI` 的暴露全部失效；现已补 include 并把暴露改成逐组 pcall。

    PrepareSwitch()   第一步：算节点 → **先写待接分支**（sg_pending）→ Network.SaveGame 存原档
    SwitchNow(reason) 第二步：**在按钮回调里**直接 Network.RestartGame()
    HasPendingSwitch() / IsSwitchSaveInFlight()   面板判断该走哪一步 / 原档是否还在写

* 为什么两步：唯一被实机证明可行的重开调用方式是**按钮回调里直接调**（第 42 条）。
  1.58~1.61 分别把重开挂在 `SaveComplete` 事件回调、按帧回调状态机里，三次都出现“点了不跳转”；
* 这条路上**没有任何“也许会不来”的环节**：不等 SaveComplete、不等按帧回调、不等时钟；
* pending 在存档**之前**写好 ⇒ 就算存档回执全丢，新局的父子关系照样成立；
* 第二次点击时若原档还在写，面板会先拦一下（`IsSwitchSaveInFlight`，宽限 12 秒；
  取不到时钟时放行并写警告），避免把存档截断；
* 重开时把门槛值一起打日志：`anyMultiplayer / savedGame / worldBuilder / isGameHost / turn`；
* 面板按钮文案：「换图（两步）」—— 第一次点存原档，第二次点重开。

#### 3.13.3c 存储内存表是「每 context 一份」（踩过）

1. **存储内存表是「每 context 一份」**：换图重开后面板是新上下文，`ModMiscStore` 的表是空的，
   不 `Refresh()` 就读不到 `sg_head` / `sg_pending` ⇒ 新局会把自己当树根（“分支不知道自己是谁”）。
   模块里统一走 `EnsureStoreReady()` 门：没就绪就等扫描完再决定，绝不拿空数据做判断。
2. **开局固化**：新局启动时探针把“本局来源（parent + kind + 地图 + 回合偏移）”
   写进随档身份 **`sgnode`**（协议 persave 通道），
   并消费掉存储里的 pending ⇒ 之后存档只依赖 CustomData（跨 context 必然可见），
   也不必担心“玩家退出后另开新局”被陈旧 pending 误挂成分支。

### 3.13.7 大表格怎么跨存档（分片 blob / 载体存档）
------------------------------------------------------------------------------

配置档名编码通道（3.9 的 `ModMiscStore`）**一个键只能塞 ~70–103 字节**（文件名 255 字节上限，
hex 后翻倍），所以大表格不能直接往一个键里塞。三条路子：

    ModMiscStore.SaveBlob(key, text)   分片：<key>$0… 每片 ≤ min(80, 按文件名算出的上限)，最后写 <key>$m
    ModMiscStore.LoadBlob(key)         拼回全文；缺片时返回 nil + "missing-chunks:<片号>"（不给半截）
    ModMiscStore.RemoveBlob(key)       连元数据与分片一起删
    ModMiscStore.GetBlobInfo(key)      { Chunks, Bytes, Missing = {…} }
    ModMiscStore.ComputeMaxValueBytes(key)   这个键还能写多少字节

    ExposedMembers.ModMiscToolUI.Carrier（载体存档，适合几十 KB 以上的表）：
        Write(name, text)   写 CustomData + 存一份 MMTBlob~<name>~<时间> 的普通档
        Read(name)          载入那份载体档之后拿到全文
        Peek() / Clear(name) / BuildCarrierName(name) / ParseCarrierName(rawName)

选型：少量短数据 → `Save`；几 KB → `SaveBlob`；大表且接收方会载入 → `Carrier`。
事件的大载荷：`SendEvent` 的 event 加 `PayloadText` 即自动走分片，收件时拼回 `event.PayloadText`。

### 3.13.9 游戏加载完成之前能不能存档 / 读档（本轮实验）
------------------------------------------------------------------------------

`UI/LoadTime_SaveProbe.lua`（**默认开**；总开关 `MODMISC_LOAD_TIME_PROBE_ENABLED`
在 `UI/Replacements/Civ6Common.lua`，分步开关在探针文件顶部）。
挂在引擎事件 `Events.LoadScreenContentReady`（游戏数据已就绪、游戏视图还没就绪 ——
`LoadScreen.lua` 注释 `-- Ready to show player info`），进对局后在
`Events.LoadGameViewStateDone` 里核对与清理。日志前缀 `[ModMiscTool][LoadTimeProbe]`。

    阶段一（载入界面）：L0 侦察（含 UI.GetSaveGameMetaData，即“正在加载的那份档”）

    阶段二（对局内）：标记活没活下来 / 探针档在不在列表里 / 删掉探针档（只认前缀）
                      没有加载期痕迹时走“只清理模式”，顺手清掉上一轮崩在半路的遗留档

判定：`lt-l0-ok` / `lt-l1-customdata` / `lt-l2-written` / `lt-l4-save-ok` /
`lt-l4-save-failed` / `lt-p2-marker-alive` / `lt-p2-marker-gone` /
`lt-p2-probe-save-listed` / `lt-p2-probe-save-missing` / `lt-p2-cleaned` / `lt-p1-missed`。

要点与坑：
* 载入界面判据不能用 `Controls.PortraitContainer` —— 那是**桌面版** `LoadScreen.xml` 的控件，
  安卓的 `LoadScreen_PHONE.xml` 没有它（只有 `Portrait`）；三个变体根节点都是
  `<Context Name="LoadScreen">`，所以认 `ContextPtr:GetID()`，控件只作退路；
* `Civ6Common.lua` 里那条 include **不做前后端过滤**：载入界面跑阶段一，对局内跑阶段二；
* 对局里 include 过 `Civ6Common` 的 context 很多、都会收到 `LoadGameViewStateDone`，

* 风险：载入期做引擎调用正是游戏自己注释里说的 “not recommended”，可能闪退；
  万一崩在载入期，探针档会留在列表里（名字带 `MMTLoadProbe` 前缀，下次进对局自动清）。

### 3.13.10 通道 E：把数据写进「模组配置组的名字」（本轮新增）
------------------------------------------------------------------------------

`UI/ModMiscModGroupStore.lua`。原版模组框架数据库里 `ModGroups.Name` 是**自由文本**
（`Base/Assets/Database/Modding.sql`，注释原文 “the user-provided name of the group”），
**不受存档名“一个文件名分量 ≤ 255 字节”那条限制**；`Modding` 组接口前端与对局内都能调
（原版 `Menus/InGameTopOptionsMenu.lua` 就在对局内用它）。

    组名格式：MMTSTORE~<hex(key)>~<3 位序号>~<hex(值分片)>     -- 一片 = 一条配置组

    ModMiscModGroupStore.IsAvailable()                 这个上下文能不能用
    ModMiscModGroupStore.List() / ListOurs()           列全部 / 只列我们的
    ModMiscModGroupStore.GetInfo()                     诊断：组数、我们的、最长名字、当前选中
    ModMiscModGroupStore.Save(key, text, chunkBytes)   先删旧片再按序建新片，写完复查
    ModMiscModGroupStore.Load(key)                     按序号拼回；缺片直接拒绝（不返回半截）
    ModMiscModGroupStore.Remove(key) / ClearAll()      删一个键 / 清掉我们全部的组
    ModMiscModGroupStore.SelfTest(sizes)               尺寸阶梯写-读-比对 + 自动清理

    ModMiscModGroupStore.BuildPayload(size)            长度恰好 size 字节的测试载荷
    ModMiscModGroupStore.SetDefaultChunkBytes(bytes)   改默认分片大小（面板「分片」选择器用它）
    ModMiscModGroupStore.ProbeNameCeiling(sizes)       逐级加长组名，量引擎的名字上限
                                                       （读回变短 ⇒ 被截断；跑完自动清理）

规则：**只碰 `MMTSTORE~` 前缀**；引擎调用全部 pcall。
**实机教训（2026-10-05，必须记住）**：`Modding.CreateModGroup` 会把新建的组设为“当前选中的组” ⇒
① 玩家的配置组选择会被改掉；② 下一次写同 key 时旧片“正被选中”删不掉 ⇒ 同序号重复 ⇒ 读回出错。
所以：写之前记住原选中组、**写完全部恢复**（`SettleSelection`）；删“当前选中的组”前先照抄原版
`FrontEnd/Mods.lua` 的 `DeleteModGroup()` —— 把选中切到别的组再删。
没有“改名”接口 ⇒ 改值 = 删旧建新。
代价：每个数据片都会出现在模组界面的配置组下拉框里（测试完请点「配置组清理」）。
**实机已验证（2026-10-05）**：64 KB = 110 片，杀进程重开后读回逐字一致；单条组名 1224 字符
被引擎原样存下。片数越多越拖累模组界面（每片 = 一条配置组 + 一份启用项副本），
所以大数据要**加大分片**而不是加片数（面板「分片」300/600/1200/2000/4000 字节）。
真实名字上限用「名字上限」按钮量。

### 3.13.11 通道 F/G 探针：引擎设置类键值存储（本轮新增）
------------------------------------------------------------------------------

`UI/ModMiscNameStoreProbe.lua`。两处引擎自己会持久化、且玩家界面看不见的键值存储：

    通道 F  useroption    Options.SetUserOption("ModMiscTool", key, 值) + Options.SaveOptions()
                          Options.GetUserOption("ModMiscTool", key)
    通道 G  userconfig    UserConfiguration.SetValue(key, 值) + UserConfiguration.SaveCheckpoint()
                          UserConfiguration.GetValue(key)

    ModMiscNameStoreProbe.GetChannels()                  两个通道的可用性
    ModMiscNameStoreProbe.GetInfo()                      当前值（跨进程验证就看这个）
    ModMiscNameStoreProbe.BuildPayload(size, tag)        造一份**长度恰好 size 字节**的载荷
    ModMiscNameStoreProbe.Write/Read/Clear(channelId,…)  写 / 读 / 清（键 = MMTProbe）
    ModMiscNameStoreProbe.SelfTest(channelId, sizes)     尺寸阶梯写-读-比对 + 清理

**实机结论（2026-10-05）：两条都不可用。**
* `useroption`：写入直接报 `MMTProbe is not a registered option.`（引擎按注册表校验选项名）；
* `userconfig`：写 4096 B 不报错，但立刻读回 `[没有这个键]` ⇒ 值没留下。

也就是说引擎只认它自己注册过的键；面板上的按钮留着以便随时复现这个结论
（「设置存储写入」= 写 4KB 并保留、「读取」= 看能不能读回、「自检」= 尺寸阶梯、「清理」= 收摊）。
跨存档存储目前只剩通道 E（模组配置组名字）这一条还没被证否 —— 复测步骤见
API_Verification_Status.md §18.4/§18.6。

### 3.13.12 大载荷门面（ModMiscBigStore，本轮新增）
------------------------------------------------------------------------------

    通道能力（都实机验证过）：
      ModMiscStore（存档名编码）      单键 ~100 B，**不用载入就能读** → 小数据（头指针/索引）
      ModMiscModGroupStore（配置组名）**1 MB / 263 片跨进程一致**，片 = 一条配置组 → 大载荷
      ModMiscCarrier（载体存档）       随档走、界面干净 → 更大的表（需要载入那份档）

    【选型铁律 · 实机 2026-10-06 换图事故换来的】容量之外还要看**落盘时机**：
      small（存档名编码）= 每个键一个小配置档，由 Network.SaveGame **排队异步**写出 ——
        一次写多个分片、紧接着重开/读档时，实测有分片赶不上落盘（4 个只到 1 个）；
      big（模组配置组）  = 模组数据库的**同步**调用，1 MB 跨进程已验证。
      ⇒ **跨重启/跨进程立刻要读的数据一律用 big**（换图交接单 sg_pending 与事件信箱 ev_* 就是因此改过去的）。
      小通道的溢出路径会打明确警告，不再沉默退化。

    ModMiscBigStore.Save(key, text)    -- 优先配置组大通道；不可用/失败自动回退 SaveBlob
    ModMiscBigStore.Load(key)          -- 先大通道，读不到再回退 blob（旧数据不用迁移）
    ModMiscBigStore.Remove(key)        -- 两条通道都清
    ModMiscBigStore.SetChunkBytes(n)   -- 分片字节数（默认 4000）
    ModMiscBigStore.GetInfo()          -- 大通道在不在 / 分片 / 现有片数

事件的大载荷已经切到这条路（`SendEvent` / `FetchEventsForNode` / `DropEventKeys`）：
发件时 `PayloadText` → 大通道，信箱记录里只留 `blobKey` 引用；收件时读回挂在 `event.PayloadText`。
**注意代价**：每片都是一条会显示在模组界面的配置组；1 MB = 263 条。大载荷请用 4000 字节/片，
数据量控制在几百 KB 内，更大的表改用载体存档。

### 3.13.13 通用数据存储协议（ModMiscDataProtocol + ModMiscDataRegistry）
------------------------------------------------------------------------------

三条铁律：**没登记不许写** / **永久数据必须写 Owner+Version** / **用后即焚的要真的焚**。

    DataProtocol.Register{ Name, Lifecycle, Channel, Owner, Version, TTL,
                           AutoDeleteOnLoad, Type, MaxBytes, Describe, Migrate }
    DataProtocol.Save(name, value) / Load(name, {keep}) / Remove(name)
    DataProtocol.SaveTree(name, root, {PartBytes}) / LoadTree(name) / RemoveTree(name)
    DataProtocol.Audit()          -- 每条盘上有没有/多大/多老 + 孤儿片
    DataProtocol.GC{ PurgeOrphans } -- 清过期 ephemeral（+可选清孤儿）
    DataProtocol.Purge(name) / PurgeAllPermanent()   -- 慎重；通配条目按前缀清现有键
    DataProtocol.SetSession / GetSession             -- 进程内数据（绝不落盘）
    DataProtocol.EnumerateKeys(spec)                 -- 某数据集现在真正在盘上的键（通配按前缀枚举）

本地模拟器（devs 仓）：`devs/BasilissaModMiscTools/Tests/protocol_transport_sim.lua`
—— 8 场景 / 48 项断言，含故障注入与真跨进程；用法见该仓 README 与 Docs/01。

生命周期：`permanent`（永久，慎重）/ `persave`（**随档**：读档还在、新局不继承）/
`session`（进程内内存）/ `ephemeral`（用后即焚，TTL）。
通道：`memory` / `save`（引擎 CustomData，persave 专用）/ `small`（存档名编码：单键 ~100B，
**超了会自动分片**，逻辑键不变，不用载入就能读）/ `big`（配置组，实测 1MB）/
`carrier`（载体档，要载入）。类型：string / number / table（table 递归，键值都支持）。

**所有存储调用一律走协议**（2026-10-05 迁移完成，旧拼串/散键/回退链已删）：
主线头 `sg_head`、待接分支 `sg_pending`（表）、事件信箱 `ev_*`（表）、事件大载荷 `evb_*`、
本局身份 `sgnode`（persave 表）、资产记录 `ModMiscAssetPlacements`（persave 表）、
建局侧 `ghost_citystates`/`ghost_majorplayers`、UI 数据 `ui_*`、探针 `probe_*`/`svprobe`。
新增 `DataProtocol.ListMatching(前缀)` 用于“按前缀取真实键”（事件信箱按节点取件）。

**换图（地图间数据传输）**：三层生命周期各就各位 ——
交接单 `sg_pending`（ephemeral/small，TTL 900s，字段含 FromMap/ToMap/Engine/PayloadKey）、
交接载荷 `xmap_*`（ephemeral/big，**读走即删**）、本局身份 `sgnode`（persave，新局开局固化
父节点/类型/地图/逻辑回合偏移）。接口：

    ModMiscSaveGraph.PrepareSwitch({ FromMap=, ToMap=, Engine=, Payload=<表> })
    ModMiscSaveGraph.SetMapHandoffPayload(payload) / TakeMapHandoffPayload()
    ModMiscSaveGraph.OnMapHandoff(fn)        -- 新局开局收到载荷（也挂在 ExposedMembers 上）

换图这一步**不写永久数据**（`sg_head` 只在正常存档时写）——桩测试第 14 节盯着这条。

**切换的判据（实机 2026-10-06 教训）**：`Events.SaveComplete` 是全局事件、认不出是哪一份存档，
**不能用它判断“原档写好了”**。唯一判据是**存档列表里查得到**：

    ModMiscSaveGraph.GetSaveState()      -- { NodeId, Name, Attempts, Verified, Failed, Elapsed, SaveCompleteSeen }
    ModMiscSaveGraph.VerifySaveNow(fn)   -- 查一次列表；查到 ⇒ Verified=true 并回调
    ModMiscSaveGraph.RetrySave(fn)       -- 未确认时重发一次（只一次）
    ModMiscSaveGraph.SwitchNow(reason)   -- **未确认一律拒绝**（返回 false, "原档还没确认落盘"）
    ModMiscSaveGraph.MarkSaveFailed()    -- 面板等够了两次之后标记失败

面板按帧每 ~2 秒查一次；40 秒未确认重发一次；再 40 秒仍无 ⇒ 报“本次没有切换”。

信封 v2：`MMT2|<生命周期>|<版本>|<写入时间>|<类型>|<名字长度>:<数据集名>|<校验和>|<负载长度>|<负载>`

> **写入时间是可选项**（2026-10-06）：只有**声明了 TTL**（或 `KeepStamp = true`）的数据集才会写它，
> 永久/随档/进程内写空字段（读出来 nil）。配合 `DataProtocol.AutoGC(reason)`：在对局 `after-load`
> 与前端加载时各跑一次自检，**只清到期的 ephemeral**，永久与随档不碰。
（v1 老信封仍可读，只做长度校验）。名字用来拦**误领**（读到别人家的数据），
校验和（FNV-1a 32）用来拦**静默损坏**（长度对得上、内容被改）。

值编码（长度前缀，二进制安全）：
    n                       nil
    b0 / b1                 布尔
    d<数字>;                数字（**%.17g**：0.1+0.2、1/3、2^53+1 都能按位还原；±inf/nan 单独标记）
    s<长度>:<字节>           字符串（含 \0 的二进制也行）
    t<个数>:[类名]{键 值…}   表格（类名可省；键值都递归）
    r<编号>;                引用（同一张表第二次出现 / 环 ⇒ **还原成同一张表**，不是复制品）
不支持的类型（函数/userdata/thread）**明确报错**，不静默丢字段。

元表：只有带 `__mmtclass = "名字"` 的表会保存类名；解码侧用
`DataProtocol.RegisterClass("名字", { OnDecode = fn })` 把行为装回去；
没登记的类照样还原字段，但 `GetLastDecodeReport().DroppedClasses` 会**如实报告**。
解码严格：长度/个数/尾部不符一律报错，不返回半截数据；信封带版本 ⇒ 结构升级给 `Migrate` 即可。

大型多层数据：`SaveTree` 把负载切 N 片存 `<name>$p1…`，头记录存 `<name>$h`
（`{Kind="tree", Bytes, Parts={{Key,Bytes}…}}`，放得下就走小通道）；`LoadTree` 逐片校验后拼回。

现有数据全部登记（见 `UI/ModMiscDataRegistry.lua`）：`sg_head`(permanent/small)、
`sg_pending`(ephemeral/small, 900s)、`ev_*`(ephemeral/small, 7d)、`evb_*`(ephemeral/big, 7d,
**故意不设读到就删**)、`blob*`/`carrier*`(permanent)、`panel`/`probe`/`nameprobe`(ephemeral/big, 1h)。
事件大载荷链路已改走协议；其余旧调用点先登记、动到哪块迁哪块。

面板「数据协议」一行：**登记表 / 审计 / GC / 清永久数据（点两次确认）**。

#### 3.14.2 回合同步（**纯逻辑**，不做硬同步）

    逻辑回合 = 引擎回合 + offset
    offset：一局内是常数，开局算一次；分支的偏移 = 起点逻辑回合 - 1
            （主线第 18 逻辑回合开的分支：引擎第 1 回合 = 逻辑第 18 回合，引擎第 3 回合 = 逻辑第 20 回合）

    ModMiscSaveGraph.GetLogicalTurn()            当前逻辑回合

    TurnEvents.SetLogicalOffset(offset)          gameplay 侧设置（UI 开局时推过去）
    TurnEvents.GetLogicalTurn()                  gameplay 侧换算

固化位置：随档身份 `sgnode` 的 `Offset` 字段（UI 侧 CustomData，协议 persave）
+ `Game:SetProperty(turnevents_offset)`（gameplay 侧）；
档名末尾可选 `~L<逻辑回合>`，身份载荷第 5/6 段是 logical/offset（老档没有 → 显示 `-`，不猜）。

#### 3.14.2b 存档策略：一条线一个档（原地覆盖）

* 本局**已有节点** ⇒ 存档沿用它的 id/父/类型，只更新内容与时间，**写成功后删掉旧文件**
  （`UI.DeleteSavedGame`）⇒“一条线只有一个格式化档”，关系树不会被同一条线的一串快照刷屏；
* 本局**还没有节点**（新开/读入非本 mod 档）⇒ 建新节点；换图后的新局第一次存档也建新节点（分支）；
* 同名（同一分钟同一回合，档名完全一致）时跳过删除，避免把刚写出来的档删掉；
* 面板另有「删除选中存档」（同样是 `UI.DeleteSavedGame`）。

换图现在是**自动**的：原档落盘确认后倒计时 8 秒自动 `Network.RestartGame()`，
期间可按「换图」立刻重开；自动没生效时 10 秒后重试一次，再不行交回手动。

#### 3.14.3 跨存档事件

    ModMiscSaveGraph.SendEvent(targetNodeId, event)     发件（写进信箱）
        event = { Type = "GOLD"|"UNIT"|"RESOURCE", Detail = <单位/资源类型名>,
                  Amount = <数量>, AcceptTurn = <接受逻辑回合>, TargetPlayerID = <玩家 id> }
    ModMiscSaveGraph.FetchEventsForNode(nodeId)         收件（返回事件数组 + 信箱键）
    ModMiscSaveGraph.DropEventKeys(keys)                投递后清理
    ModMiscSaveGraph.GetInheritedNodeIds()              本局要**继承**哪些节点的信箱（见下）
    ModMiscSaveGraph.IntakeEvents(onDone)               收件 → 交给 gameplay 的回合事件列表
        收件目标 = 本局节点（可能有）+ 继承来的逻辑档 id；继承来的事件会带 InheritedFrom 字段

    ExposedMembers.ModMiscToolScript.TurnEvents（gameplay）：
        SetLogicalOffset(offset) / GetLogicalOffset() / GetLogicalTurn()
        AddIncoming(event)      入列（过期 ⇒ 排到下一回合触发）
        GetAll() / Clear() / ProcessDue(reason)
        TriggerEvent(event)     **只触发**（问处理器），核心不自己执行
        RegisterHandler(type, fn, priority) / UnregisterHandler(type, fn)
        ClearHandlers(type) / GetHandlerTypes()

    ExposedMembers.ModMiscToolScript.TurnEventHandlers（gameplay，**默认处理方式**）：
        Enable() / Disable() / IsEnabled()   开关整套默认处理器
        GetHandlers()                        当前注册情况（诊断）

    **执行方式不写死**（授权者 2026-10-05 定）：核心只负责“到点触发 + 广播”，
    触发之后干什么由处理器决定：
        handler(event) → ("handled" | "defer" | "failed", detail)
        * handled / failed → 出队（failed 的 detail 会进提示文案）
        * defer            → 留在队里，下一回合再问（例如接收方还没首都）
        * 其它/nil         → 这个处理器不管，继续问下一个
        同类处理器按优先级降序询问；没有任何处理器认领 → **事件留在队列里**（不静默丢）。
    默认那套（金币→国库、单位→首都、资源→库存或地图）只是当前测试框架的实现：
    别的 mod 注册更高优先级即可接管，或先 Disable()/ClearHandlers() 再自己来。

**信箱**：跨存档存储键 `ev_<目标节点id>_<序号>`，值是**协议编码的表**
（`Type/Detail/Amount/AcceptTurn/FromNode/FromPlayerID/FromCiv/Stamp/PayloadKey`；
大载荷另存 `evb_*`，信箱里只留引用）。一个事件一个键，**投递即删**。

**切到逻辑占位之后的信箱继承（v1.99）**：占位在重开前就被移除，可它的信箱键是
`ev_<占位id>_*`，而新局的节点 id 是后来才生成的 ⇒ 不处理的话“发给某个逻辑档的事件”
永远收不到（静默丢失）。所以：

  * `PrepareSwitch` 把占位 id 写进交接单（`InheritNodeId`）；
  * 新局开局探针固化身份时记进 `identity.InheritIds`（随档走，存档写身份时**不会**被覆盖掉）；
  * `IntakeEvents` 把“本局节点 + 继承来的 id”都扫一遍，继承来的事件带 `InheritedFrom = <占位id>`；
  * 换图**之前**那一局不会认领（`GetInheritedNodeIds` 只在“本局还没有身份”时才读交接单），
    否则那边点一次「收件」就会把占位的信箱提前领走、新局反而收不到。

**发放通道**：金币 = `ChangeGoldBalance`；单位 = `UnitManager.InitUnit` 落在接收方首都（没首都顺延）；
资源 = 先探 `GetResources():ChangeResourceAmount`，不行就 `WorldBuilderAPI.SetResourceType` 落到首都附近的地块。

**文本提示（其它 mod 可定义）**：

    LuaEvents.ModMiscToolTurnEventFired.Call(type, detail, amount, fromNode, overdue, toPlayerID, result,
                                             inheritedFrom)   -- 第 8 个参数可空；旧 7 参调用兼容
    LuaEvents.ModMiscToolTurnEventBatch.Call(count, logicalTurn)
    ExposedMembers.ModMiscToolUI.RegisterTurnEventTextResolver(fn)
        fn(eventType, detail, amount, fromNode, overdue, toPlayerID, result) -> 文本或 nil

默认文案：`LOC_MODMISC_TURNEVENT_{GOLD,UNIT,RESOURCE,UNKNOWN,TITLE,OVERDUE_SUFFIX}`。

### 3.13.14 存档面板：换图 = 写广播 + 直接重开；关系可手动改（v3.00 起）
------------------------------------------------------------------------------
动机与实机证据见 API_Verification_Status.md §19.26（旧的两步式 + 落盘确认已废弃）。

按钮语义（UI/ModMiscSavePanel.lua）：

  按钮                 行为
  -----------------    ------------------------------------------------------------
  存档                 直接存（M/B 自动判；本局已有节点则原地覆盖同名线）
  重开为新分支         ① 第一次点：确认；② 第二次点（按钮回调里）：查主线存档 →
                       写换图广播 → Network.RestartGame()。**不写任何存档**
  载入选中 / 删除选中  先确认（弹窗，或本上下文没有弹窗时“再点一次确认”）
  本档→主线            把本档设为主线（M）
  本档→分支            把本档设成分支（B），父 = 选中的档（没选就挂主线头）
  选中→主线 / 选中→分支 把选中的那条档改成主线/分支（分支的父 = 本局节点或主线头）
  收件 / 刷新列表      直接执行

换图的门槛与广播（UI/ModMiscSaveGraph.lua）：

  GetMainlineAnchor() -> (id, 来源说明)   主线档在哪：主线头 / 列表里的主线档 / 本局就是主线档
  HasMainlineSave() -> (bool, 原因)       **没有主线存档就拒绝换图**（要求玩家先手动存档）
  BroadcastBranchSwitch({ Parent? })      写广播 sw_bcast（ephemeral/big，TTL 300s）
  PeekBranchBroadcast() / TakeBranchBroadcast() / ClearBranchBroadcast()
                                         看 / 取（读到即删 = 用后即焚）/ 清
  SwitchToNewBranch({ Reason? })          门槛 → 写广播 → 直接 Network.RestartGame()
  RestartNow(reason)                      只重开（诊断用）

  广播字段：{ Parent, Kind="B", Logical（逻辑回合锚点）, Turn, Map, FromNode, Stamp, WrittenAt }
  新局开局（ReportAfterLoad）：先清过期（AutoGC + 300 秒自检），再检测广播 →
  **有就一律认定本局是分支**（父/锚点取自广播）→ 立刻删掉广播。
  已知漏洞（授权者接受）：这 5 分钟内开的任何新局都会被当成分支；
  若本局已有自己的身份，则不改本局关系、只消费广播（日志写明）。

手动改关系（档名改不了 ⇒ 关系覆盖表 sg_over，permanent/small）：

  SetCurrentRelation(kind[, parentId])    本档设为主线/分支（同时改写本局身份）
  SetNodeRelation(id, kind[, parentId])   别的档设为主线/分支（父不能是自己）
  ClearNodeRelation(id) / ListRelationOverrides()
  覆盖在“读列表 → 建树”之间套用（节点上带 Overridden 标记，树里显示「手动改过关系」）；
  本局自己那条同时改写身份 ⇒ 下次存档把新关系写进档名，自然收敛。
